**Victor's standing rules, binding on every part of this document:**

- The panel is locked until a person unlocks it with their own bearer token ("linked"). A system admin
  can let people in to **watch only**. Interactive features are linked-only, and the server enforces it
  (`server/access.go` `routeClasses` and `accessOf`). Connecting an account is interactive.
- Browsers contact nobody but the Mattermost server, apart from stated exceptions. Today there are two,
  both Twitch's (its player, and Connect Twitch). **3.4.0 adds two more, Connect Steam and Connect
  Hytale**, and states them honestly everywhere, as Twitch's were (§7).
- Tokens and secrets are never logged and never sent to browsers. Secret settings are masked and left
  out of backups unless ticked.
- Preview (screenshots of 2 or 3 options) before any visible UI is built. Calm, minimal UI that matches
  the plugin: black, the emblem, Oswald capitals, the plugin red, and the one quiet footer bar whose small
  tools open sheets that rise from the bar, one at a time.
- The footer bar already has six tools (the soundboard, What's on?, clips of your stream, the relink
  key, Twitch, plan), and below a 360 px panel the stream title is down to its pencil. **3.4.0 adds no
  footer tool** (§5.2).
- The lock screen shows nothing but the emblem, the bar and status, plus the Disconnect key a
  connection needs. It does not advertise being let in and shows no admin lines.
- Only Mattermost 11.11 is supported (React 18.2.0). Server builds are `CGO_ENABLED=0`, Go 1.27.2 (moved to 1.27.4 at release for two standard-library fixes; `design/STATUS.md`).
- Mattermost, Steam and Hytale behaviour is verified in real sources, never from memory.
- Victor's e-mail address goes nowhere: not into a setting, a page, a test, a log or an outbound
  request.

**How this relates to the other contracts.**

- `design/twitch-live.md` (3.1.0) is the **template**. Its ticket, state, nonce, callback pages,

### 2.2 The provider descriptor

```go
// accountProvider is one service a person can connect besides Twitch. Each
// one's paths, KV keys, words and checks come from here, so a ticket, a state
// or a notice of one service can never be spent, read or shown as another's.
type accountProvider struct {
    id        string // "steam" | "hytale": KV prefixes and paths are built from it
    name      string // "Steam" | "Hytale", in words
    linksKey  string // "steam_links" | "hytale_links"
    maxLinks  int    // 100 each: one GetPlayerSummaries call's limit (S10), and plenty for this server
    on        func(cfg *configuration) bool
    // setup is "" when people can connect, otherwise the sentence an admin is shown.
    setup     func(p *Plugin, cfg *configuration) string
    // start writes what the provider needs into the state and returns where the
    // browser (or Matty's sign-in window) is sent.
    start     func(p *Plugin, cfg *configuration, state string, st *accountState) (location string, err error)
    // finish turns what came back into a proof, or a refusal with a code word.
    finish    func(ctx context.Context, p *Plugin, cfg *configuration, state string, st accountState, query url.Values, now time.Time) (accountProof, *accountRefusal)
}

type accountProof struct {
    ID     string // Steam: SteamID64, decimal; Hytale: profile uuid, lower case
    Name   string // Steam: the Steam name ("" if Steam's answer was late); Hytale: the username
    Hidden bool   // Steam only: the profile is not public
}

// accountRefusal is a page id and a code word: the page for the browser, the
// code for Matty's app-finish, the reason (fixed words only) for the log.
type accountRefusal struct {
    page, code, reason string
    status             int
}
```

The two descriptors, `steamProvider` and `hytaleProvider`, are package variables, and so are the
provider hosts they use (`steamOpenIDBase`, `steamAPIBase`, `hytaleBase`), which the tests swap for a
fake, as `twitchIDBase` is swapped today.

### 2.5 Connecting: the ticket, the connect page, the callback

The template's three requests, each guarding the next (`design/twitch-live.md` §4.2-§4.3), with the
provider's two hooks where Twitch has its authorize URL and its proof.

**`POST /api/v1/{p}/connect-ticket`** (the panel, on the first press of Connect). In order:

- T1. `no-store`. Not an interactive session: 403 `interactive_only`.
- T2. `!p.on(cfg)`: 404 `off`, "Connecting Steam accounts is switched off on this server."
- T3. `p.setup(…) != ""`: 503 `setup`, the sentence for admins, "An admin needs to finish
  setting up Steam." for everybody else.
- T4. The links document cannot be read: 503 `store`. The caller is blocked: 403 `blocked`, "An admin
  has turned off Connect Steam for your account."
- T5. The service's connect limiter refuses: 429 `rate_limited`, "Too many tries. Wait a few minutes
  and press Connect Steam again." The only place a web attempt is counted.
- T6. `ticket = randomHex(32)`; `KVSetWithExpiry(p.id+"_ticket_"+userID, {h: hashHex(ticket), s:
  c.SessionId, at}, 600)`; a failure is 503 `store`. One per person per service: a new one replaces
  the old.
- T7. 200 `{"ticket":"<64 hex>","expiresIn":600}`.

**`GET /api/v1/{p}/connect?t=<ticket>`** (opened by the panel with `window.open` on the second
press). Steps C1-C6 write nothing, count nothing and redirect nowhere:

- C1. The HTML headers (§2.8). Not exactly the path, or not GET: 404 page `stale`.
- C2. Fetch metadata: `Sec-Fetch-Dest` present and not `document`, or `Sec-Fetch-Site` present and
  neither `same-origin` nor `none`: 400 `stale`.
- C3. No `Mattermost-User-Id`, or not interactive: 401 `signin`.
- C4. `accessOf(user)`: a store error is 503 `store`; not linked is 403 `locked`.
- C5. `t` not `^[0-9a-f]{64}$`: 400 `stale`. `KVGet(p.id+"_ticket_"+user)`: empty, 400 `stale`; error,
  503 `store`. Decode; `hashHex(t)` must equal `h` and `s` must equal `c.SessionId`, both with
  `subtle.ConstantTimeCompare`; otherwise 400 `stale`, and the stored ticket is left alone.
- C6. Spend it: `KVCompareAndDelete(key, raw)`; false is 400 `stale`. **The first write.**
- C7. Off: 404 `off`. Setup problem: 503 `setup` (admins see the sentence). Links unreadable: 503
  `store`. Blocked: 403 `blocked`. Not connected and already `maxLinks` people: 409 `full`.
- C8. `state = randomHex(32)`. `st = accountState{Provider: p.id, User, Session: c.SessionId, At,
  Mode: "web"}`; `location := p.start(p, cfg, state, &st)` fills `Return` (and for Hytale `Nonce` and
  `Verifier`). A start error is 503 `setup`.
- C9. `KVSetWithExpiry(p.id+"_state_"+state, st, 600)`; failure, 503 `store`.
- C10. `Location: <location>`, 302.

**`GET /api/v1/{p}/callback`.** Steps K1-K5 make no outside request, so nobody can make the server
call Steam or Hytale without a live state of their own:

- K1. The HTML headers. Not exactly the path, or not GET: 404 `expired`.
- K2. `state := query.Get("state")` must match `^[0-9a-f]{64}$` and must be the **only** `state`
  value in the query; otherwise 400 `expired`.
- K3. `KVGet(p.id+"_state_"+state)`: empty, 400 `expired`; error, 503 `store`. Decode. Undecodable,
  `st.Provider != p.id`, `st.User == ""`, `now - st.At > 600 s` or `st.At > now + 600 s`: delete it,
  400 `expired`.
- K4. Spend it: `KVCompareAndDelete`; error 503 `store`; false 400 `expired`. Every outcome after this
  has used the state up.
- K5. **`st.Mode == "app"`: 400 page `app`, and nothing else happens.** A sign-in started by Matty can
  only be finished by Matty (§6.5); a browser that arrives here with such a state, by accident or
  because somebody sent it a link, links nothing, and the state is gone.
- K6. No `Mattermost-User-Id`, or not interactive: 401 `signin`. `Mattermost-User-Id != st.User`: 403
  `otheraccount`. **The account-linking defence**, exactly as Twitch's (V9).
- K7. `accessOf` again: store error 503 `store`; not linked 403 `locked` (a state lives ten minutes,
  and an unlink or a let-out inside them must still stop it).
- K8. The provider's own "came back without an account" check (Steam §3.4 step S1, Hytale §4.4 step
  Y1): `cancelled` (200, with Close) or the provider's error page.
- K9. Off: 404 `off`. Blocked: 403 `blocked`.
- K10. `proof, refusal := p.finish(ctx15s, …)`. A refusal answers its page and status.
- K11. The switch again (it may have gone off during K10): 404 `off`. Then
  `setAccountLink(p, user, proof, state.at, now)` (§2.6). `errAccountFull` 409 `full`, `errAccountBlocked`
  403 `blocked`, `errAccountCleared` (a state made no later than the last Delete all) 400 `expired`,
  anything else 503 `store`.
- K12. Afterwards: the loop's links cache is updated (for Steam, the new person's first status seeded
  from the proof, offline and `hidden` as it says, until the next read) and the loop kicked (§2.13);
  `account_link` to the user, and to the previous owner after a takeover; the view rebuilt (§2.9);
  `LogInfo("Somebody connected their Steam account", "user_id", user)`.
- K13. 200 page `connected` with the name (and, for Steam, the hidden-profile sentence when
  `proof.Hidden`; for both, the takeover sentence when the account moved).

The ticket, the state, the nonce, the verifier, any code, token or ID token, and every `openid.*`
value never appear in a log, an error string, KV (apart from the state record's own fields) or a page.

### 2.6 The link documents

`steam_links` and `hytale_links` share one Go shape and one set of functions, each called with the
provider:

```go
type accountLinks struct {
    V       int                    `json:"v"`
    Users   map[string]accountLink `json:"users"`
    Blocked map[string]int64       `json:"blocked,omitempty"` // Mattermost user id -> when, ms
    Lost    map[string]accountLost `json:"lost,omitempty"`    // takeover notices, by previous owner
    Cleared int64                  `json:"cleared,omitempty"` // when Delete all last wrote it, ms (build review sec-1)
}
type accountLink struct {
    ID   string `json:"id"`
    Name string `json:"name"`
    At   int64  `json:"at"`
}
// accountLost is a takeover notice. ID is the account that moved, kept only so
// that removing that account removes the notice too (V31); it stays on the
// server and is never in /me, which gets a meLost.
type accountLost struct {
    ID   string `json:"id"`
    Name string `json:"name"`
    At   int64  `json:"at"`
}
type meLost struct {
    Name string `json:"name"`
    At   int64  `json:"at"`
}
```

- **Decode**: nothing stored is an empty v1 document; bytes that will not decode, or another version,
  are `errAccountLinksUnreadable` (wrapping `errStore`), quarantined once and never overwritten.
- **Invariants**: an `id` appears under at most one user; a user has at most one `id` per service; at
  most 100 users and 500 blocked; a blocked user has no `users` entry; `lost` entries older than 30
  days are dropped on every write; **no `lost` entry names an account that has been removed**.
- **`setAccountLink(p, user, proof, startedAt, now)`**, the apply function: a connection whose state was
  made no later than `cleared` is `errAccountCleared` (it started before a Delete all and is still
  finishing; the check sits in the same compare-and-set as the write, so it holds on a cluster); blocked
  is `errAccountBlocked`;
  `previous := owner(proof.ID)`; if it exists and is not `user`, delete `users[previous]` and set
  `lost[previous] = {proof.ID, name, now}` (**a verified proof wins**, as for Twitch and stream keys);
  delete `lost[user]`; a newcomer at the cap is `errAccountFull`; if `user` had another account,
  `dropNotices(old.ID)`; write `users[user] = {proof.ID, proof.Name, now}`. Replacing one's own
  account with another needs nothing more: neither service has derived data.
- **`dropNotices(id)`** deletes every `lost` entry whose `ID` equals `id`. It runs inside the same
  `casUpdate` apply function as every removal of an account: Disconnect, the admin's `?user=` removal
  with or without `block=1`, `POST …/block` with `blocked: true`, and `setAccountLink`'s replacement
  above. This is the template's purge step 5 (V31) without a purge worker: a takeover notice holds the
  name of an account that moved, and once that account is disconnected nobody keeps its name. The
  person who had the notice loses it; that is the template's choice too.
- **Blocking is by Mattermost id only**, per service. A list of blocked Steam or Hytale ids would keep
  data about people who withdrew.
- **Renames** (Steam only): the loop writes a changed Steam name with `casUpdate`, only when it really
  changed and passes `cleanText` (at most 64 runes). The apply function changes `users[u].Name` **only
  when `users[u]` exists in the fresh document and its `ID` equals the SteamID that was read**, and
  never creates an entry (V32), so a rename can never bring back a link deleted while the read was out.
  Hytale names change only by connecting again.

### 2.7 Disconnecting, notices and Delete all

**`DELETE /api/v1/{p}/link`** and the admin's `?user=`, **whatever the switch says**: one `casUpdate`.
No entry: change nothing, 200 `{"ok":true}` (idempotent; with `block=1` it still sets `blocked`). Nothing
means nothing: no install, no view rebuilt, no kick and no `account_link` (the route is open to every
session and not metered, and a kick brings Steam's next call forward). The same holds for a notice's
OK with no notice, an unblock of somebody not blocked and a Clear of an empty list.
Otherwise delete `users[user]` and `dropNotices(users[user].ID)` (§2.6). Then: install the written
document as the loop's cached one and bump the link-write counter (§2.13), forget that person's status
in memory, rebuild the view, kick the loop, `account_link` to that user. A store failure: 503 `store`,
"VillaNET could not disconnect Steam just now. Try again in a moment."

**No purge worker.** Twitch needs one because Twitch hours are derived data in other documents
(`twitch-live.md` §4.6). Steam and Hytale keep nothing but the link entry and any takeover notice
naming the account: the status, the game and the "online" state live only in the loop's memory and go
with the entry, and the notices go in the same write (§2.6). One write deletes everything.
If a later version ever stores Steam playtime or a "last seen", the purge pattern comes back with it.

**Withdrawal never depends on the switch**, for the template's reason and the Steam terms' (S14:
"delete" on ending), so a person can always remove their account, and an admin can always remove
anybody's.

**`POST /api/v1/{p}/notice`**: deletes `lost[user]`; 200 `{"ok":true}`; idempotent.

**`DELETE /api/v1/admin/{p}?all=1`** ("Delete all Steam data" / "Delete all Hytale data"), whatever the
switch says, in this order:

1. Take the accounts loop's `runLock`; stop the loop and wait (it ends within one request, §2.13).
2. Rewrite `p.linksKey` by `casUpdate` to a fresh document holding only its `blocked` map and
   `cleared`, the time of this Delete all, written even where nothing was stored (a read the store
   refuses writes nothing, so the block list is never lost); delete `quarantine_<linksKey>`; delete
   every `<p>_ticket_`, `<p>_state_` and (Steam) `steam_nonce_` key `kvKeysWithPrefix` finds. A
   connection already past its state when Delete all runs is still talking to the service; `cleared`
   is what refuses it when it comes back (§2.6), so nothing is written after Delete all.
3. Clear that service's memory (statuses, the cached document, the failure state).
4. Start the loop again if any switch is on; release `runLock`.
5. Rebuild the view; `account_link` to everybody (`WebsocketBroadcast{}`); answer `{"ok":true}`.

Clearing the block list is `POST /api/v1/admin/{p}/block {"all":true,"blocked":false}`.

**`GET /api/v1/accounts`** (`routeWatch`, `no-store`), from memory: the view the loop and every link
write keep built. **Not in the snapshot and not on `/streams`**, both of which reach locked people
(V14).

```jsonc
{
  "v": "3f2a9c01b7de",            // first 12 hex of sha256 of "people" as sent; changes only when it does
  "steam":  {"on": true, "fresh": true, "at": 1794430000000},   // fresh: a good read in the last 5 min; at: that read

    "4xq8r1…": {
      "steam":  {"name": "Dave", "url": "https://steamcommunity.com/profiles/76561197960287930",
                 "state": "online", "inGame": true, "game": "ELDEN RING"},

```

- `people` holds every Mattermost user with a connection to a service that is **on**, skipping
  deactivated users (`DeleteAt != 0`), users `GetUsersByIds` no longer returns (permanently deleted),
  and anybody blocked. The lookup is one `GetUsersByIds` per step, made **before** the Steam read, and
  its answer decides both whom Steam is asked about and who is in the view (§2.13). A service that is
  off contributes nothing, and says `{"on": false}`.
- The view is always built from the loop's **cached** links document joined to the statuses by
  SteamID, never from a step's own copy (§2.13).
- `steam.state` is `online`, `busy`, `away` or `offline` while `fresh`, and `""` otherwise (names and
  links still shown, statuses not guessed). `steam.inGame` is true, and `steam.game` holds the game's
  name (possibly `""`), only while Steam reports a game for a public profile (§3.7). Nothing says that
  a profile is private: to others it is offline.
- Keys are user ids, sorted (Go's map encoding), so the same people give the same bytes and the same
  `v`.
- At 100 + 100 people the answer is about 20 KB at worst; on an eight-person server under 2 KB.

**Snapshot: unchanged.** Nothing about Steam or Hytale is added to the snapshot, to `/streams` or to
the `streams` event, and the golden snapshot test stays byte-identical (A1).

**WebSocket.** Two new events, both with an **empty payload** (`map[string]any{}`), so Matty's
`str("payload")` rule is never in play (A4):

| Event | To | Means | Sent when |
|---|---|---|---|
| `accounts` (`custom_ceo.villa.villanet_accounts`) | everybody (`WebsocketBroadcast{}`) | "`GET /api/v1/accounts` again, if you may watch" | the view's `v` changed; at most once per 10 s, trailing (a burst of changes is one event) |
| `account_link` (`custom_ceo.villa.villanet_account_link`) | one user (`WebsocketBroadcast{UserId}`), or everybody after a Delete all | "`GET /api/v1/me` again" | that person's Steam or Hytale connection, block or notice changed |

The `accounts` event goes to everybody because a broadcast cannot name a set of users (M5); it carries
nothing, and a locked reader who reads again gets the gate's 403. What a locked person can learn from
it is that something changed at that moment, which the README states (§7.2). `twitch_link` is unchanged and
is never sent for Steam or Hytale.

### 2.13 The accounts loop, the lifecycle, and the lock order

One loop, `server/accounts_live.go`, serves both services. It is the template's loop shape
(`twitch_live.go` §5.2 there) without anything Helix-specific:

- A store made on first use that outlives restarts of the loop, holding in memory only: each service's
  cached links document and its **link-write counter**, the Steam statuses and their read time, the
  failure state, the day's call count (for the admin card), the built view and its `v`, and the two
  connect limiters.
- `run()` steps, then waits on `nextAt`, a kick or the context. A kick runs a step no sooner than 10 s
  after the last and never cuts short a backoff or a wait Steam asked for.
- `step()`, in order:
  1. For each service that is on, note its link-write counter, then read its links document fresh (one
     KV read; an unreadable one is quarantined once and contributes nothing).
  2. One `GetUsersByIds` for every connected user of every service that is on. A user it does not
     return, or returns with `DeleteAt != 0`, is left out of everything below. An error ends the step
     here: Steam is asked nothing and the last view stands until the next step.
  3. If Steam is on and an active person is connected: the Steam read (§3.5), for the active people's
     SteamIDs only.
  4. Rename write-backs (§2.6's rule: an existing entry with the same id only).
  5. Install each fresh read as the cached document **only if that service's link-write counter is
     still what step 1 noted**; otherwise keep the newer cached copy a link write installed.
  6. Build the view from the cached documents (rule 2 below); publish `accounts` if `v` moved
     (debounced 10 s).
- **Four rules keep a Disconnect from coming back** while a step is out (up to the 10 s request
  budget):
  1. Every link write (connect, takeover, disconnect, block, unblock, a notice, the admin's removal,
     Delete all, and the loop's own rename write-back) installs its own `casUpdate` result as the
     cached document and bumps the counter, under `accounts.lock`, **before** the view is rebuilt. (A
     step whose own rename bumped the counter therefore keeps the rename's newer result at step 5.)
     Each service's link writes on a node hold its write lock from the read before the compare-and-set
     to that install, so writes landing at once are cached in the order they were saved; a write that
     changed nothing installs nothing (build review srv-4).
  2. The view is always built from the cached document, joined to the statuses by SteamID. A status
     whose SteamID no cached entry holds is dropped, never shown.
  3. A step installs its fresh read only when no link write happened since that read began (step 5).
  4. A rename changes an existing entry with the same id and never creates one (§2.6).
- **Deactivation.** `UserHasBeenDeactivated` (X2) is implemented: it drops that person's Steam status,
  rebuilds the view (the person leaves `/accounts` at once) and kicks the loop. A reactivated person is
  asked about again from the next step. Nothing is deleted: the link stays until the person or an
  admin removes it, and the admin card marks such people (§3.8).
- The loop runs only while `steamOn() || hytaleOn()`. While Hytale alone is on it still steps once a
  minute (one KV read), because the view is each node's own memory and a link write rebuilds only the
  node that served it: on a cluster, a connection made on another node shows within a minute, as
  Twitch's loop also reads its links fresh every pass.
- `OnActivate`: `restartAccountsLive()` after `restartTwitchLive()`. `OnDeactivate`: `stopAccountsLive()`
  beside `stopTwitchLive()`, waiting for it. `OnConfigurationChange`: restart only when
  `!sameAccountsLive(previous, cfg)`. Switching a service off clears its statuses and rebuilds the view
  at once, so its rows go on the next event. Changed Steam settings lift Steam's hold; changed Hytale
  settings (switch, Client ID or Client Secret) forget what the last sign-in said was wrong with the
  application, so an admin who has just fixed it is not told to fix it again (build review srv-1).
- **Lock order**: `accounts.runLock` (lifecycle), then a service's write lock (its link writes), then
  `accounts.lock` (data). No stats lock is ever
  taken. Stopping waits with no lock held; every request in a step uses the loop's context, so a stop
  ends within one request (at most 10 s).

## 3. Steam (part B)

### 3.1 What it is

A linked person presses **Connect Steam**, signs in on Steam's own page, and comes back connected.
From then on, everyone who can open the panel sees their Steam name, whether Steam says they are
online, busy or away, and the game they are playing, if their Steam profile is public. Nothing is
asked of Steam while the switch is off.

### 3.2 Setting it up

1. **Make a Steam Web API key** at `steamcommunity.com/dev/apikey` with the Steam account that will
   own it: domain name = the host of the Site URL (S16). The account must have spent 5 USD and use the
   Steam Guard Mobile Authenticator (S16, S17). Paste it into **Steam Web API key**.
2. Switch on **Show people's Steam status**.
3. Nothing else: **Steam has no redirect address to register** (S1, S4). The `SteamSetup` card shows the
   address Steam sends people back to and the realm Steam's page names, for reference only.

`steamCallbackURL(siteURL)` is `twitchCallbackURL`'s rules with its own sentences: the Site URL must be
set ("Mattermost's Site URL is not set (System Console > Environment > Web Server > Site URL), so Steam
has nowhere to send people back to."), readable, and https, or http only on `localhost`,
`127.0.0.1` or `[::1]` ("Steam's sign-in needs an https:// address to send people back to, and the
Site URL is http://…"). The address is `strings.TrimRight(siteURL, "/") +
"/plugins/ceo.villa.villanet/api/v1/steam/callback"`. The realm is the Site URL's scheme and host
(with any non-default port), no path, no trailing slash: what Steam itself fills in (S4). A Site URL
with a sub-path still works, because the origin is a parent of every path (S6's realm rule).
`steamProvider.setup` is that problem, or "Fill in the Steam Web API key first.", or the key-shape
sentence (§2.10), or "".

### 3.3 Start: `steamStart`

`st.Return = steamCallbackURL + "?state=" + state`. The location is `steamOpenIDBase + "/openid/login?"`
and these parameters **in this order**, each escaped with `url.QueryEscape`, so tests compare the
string:

| # | Name | Value |
|---|---|---|
| 1 | `openid.ns` | `http://specs.openid.net/auth/2.0` |
| 2 | `openid.mode` | `checkid_setup` |
| 3 | `openid.return_to` | `st.Return` |
| 4 | `openid.realm` | the realm |
| 5 | `openid.identity` | `http://specs.openid.net/auth/2.0/identifier_select` |
| 6 | `openid.claimed_id` | `http://specs.openid.net/auth/2.0/identifier_select` |

`steamOpenIDBase` is `https://steamcommunity.com`, a variable only so tests can point it at a fake.
**Discovery is never run**: the endpoint is hard-coded, as xPaw advises (S9). The server makes no
request at this step. Steam's sign-in cannot be framed (S7), so it is always a top-level window.

### 3.4 Finish: `steamFinish`

Called at K10 with the spent state; steps S1-S9 make no outside request. Every refusal carries a fixed
reason word, logged once per kind with the user id; nothing Steam sent is logged.

- S1. **Mode.** `openid.mode == "cancel"`: page `cancelled` (this is K8). `"error"`: page
  `providererror`, reason `steam_error` (Steam's `openid.error` text is never logged or shown). Not
  `"id_res"`: page `expired`, reason `mode`.
- S2. **The fields.** Every query key that starts with `openid.` must be one of exactly these ten, each
  present **once**: `ns`, `mode`, `op_endpoint`, `claimed_id`, `identity`, `return_to`,
  `response_nonce`, `assoc_handle`, `signed`, `sig`. A missing, unknown or repeated one: page
  `providererror`, reason `fields`. (Repeated keys would let what VillaNET checks and what Steam checks
  be different values.) Each value at most 512 bytes, `return_to` at most 1024, the whole query at most
  8 KiB: page `expired`, reason `size`.
- S3. `openid.ns == "http://specs.openid.net/auth/2.0"`, else reason `ns`.
- S4. `openid.op_endpoint == steamOpenIDBase + "/openid/login"`, else reason `op_endpoint`.
- S5. `openid.claimed_id == openid.identity`, and identity matches
  `^https://steamcommunity\.com/openid/id/(76561[0-9]{12})/?$` (xPaw's pattern, S8: the host is literal
  and its dots escaped, https only), else reason `identity`. The 17 digits are kept as a **string**
  (they fit a `uint64`, never a float or a JavaScript number).
- S6. `openid.signed` is exactly `signed,op_endpoint,claimed_id,identity,return_to,response_nonce,assoc_handle`
  (S8), else reason `signed`. So Steam's signature covers `return_to`, and with it the state: an
  assertion cannot be moved to anybody else's state without `check_authentication` failing.
- S7. `openid.return_to == st.Return`, byte for byte, else reason `return_to`. With K2 this is OpenID's
  "matches the current request" check (S6): the same scheme, host and path, and the one parameter in
  it present with the same value.
- S8. `openid.response_nonce`: at most 255 characters, starting with an RFC 3339 UTC time
  `YYYY-MM-DDTHH:MM:SSZ` within 300 s of now either way (S8), else reason `nonce_time`.
- S9. **Never twice.** `KVSetWithOptions("steam_nonce_"+hashHex(nonce), {"at":now},
  {Atomic: true, OldValue: nil, ExpireInSeconds: 600})` (M4). False: page `providererror`, reason
  `nonce_reuse`. An error: page `store`. Written before S10, so two callbacks carrying one assertion
  cannot both pass.
- S10. **Ask Steam.** `POST steamOpenIDBase + "/openid/login"`, `Content-Type:
  application/x-www-form-urlencoded`, body exactly the ten fields with `openid.mode` changed to
  `check_authentication`, and nothing else (not `state`). Through `sendMedia`, on a 10 s budget inside
  the callback's 15 s. 403 or 429: page `busy`, reason `slow` (Valve rate-limits this endpoint, S8).
  Any other non-200: page `providererror`, reason `status` with the status. The body (at most 4 KiB) is
  read as Key-Value lines; it must hold `ns:http://specs.openid.net/auth/2.0` and `is_valid:true`
  exactly, else page `providererror`, reason `is_valid`.
- S11. **The name.** One `GetPlayerSummaries` for this SteamID (§3.5's request), on a 5 s budget.
  A failure is not a refusal: the link is written with an empty name and the loop fills it in within a
  minute. It is counted in the day's calls the admin card shows.
- S12. The proof: `{ID: steamID, Name: cleaned personaname, Hidden: communityvisibilitystate != 3}`.

**Replay, three ways.** The state is single-use and server-side (K3-K4); `return_to`, and so the
state, is inside Steam's signature (S6); and the response nonce is recorded and time-boxed (S8-S9).
Whether Steam itself refuses a second `check_authentication` for one nonce, as OpenID requires, is
UNVERIFIED and nothing depends on it.

### 3.5 The Steam read (in the accounts loop)

| Constant | Value | Why |
|---|---|---|
| `steamReadEvery` | 60 s | Statuses change by the minute; one call a minute is 1,440 a day (1.4 % of S14's 100,000) |
| `steamKickGap` | 10 s | A connect shows within seconds without letting kicks flood Steam; even a kick every 10 s all day would be 8,640 calls, so no daily cap is needed |
| `steamKeepGood` | 5 min | After that, statuses are not guessed: `fresh: false`, states `""` |
| `steamRequestBudget` | 10 s | The one call |
| `steamBackoff` | 60 s doubling to 10 min | Failures |
| `steamSlowDown` | 2 min doubling to 10 min | A 429 |
| `maxLinks` (Steam) | 100 | S10's limit for one call, so a pass is always one call |

**The request.** `GET steamAPIBase + "/ISteamUser/GetPlayerSummaries/v2/?steamids=<ids joined by
commas>"` with headers `x-webapi-key: <key>` and `Accept: application/json` (S15). **The key is never
in the address**, so neither Go's `*url.Error` (S19) nor any proxy log can carry it; `sendMedia` still
strips the address from errors. `steamAPIBase` is `https://api.steampowered.com` (S10), a variable for
tests. The answer is capped at 1 MiB and decoded as:

```go
type steamSummaries struct {
    Response struct {
        Players []struct {
            SteamID    string          `json:"steamid"`
            Name       string          `json:"personaname"`
            State      int             `json:"personastate"`
            Visibility int             `json:"communityvisibilitystate"`
            GameName   string          `json:"gameextrainfo"`
            GameID     json.RawMessage `json:"gameid"` // only whether it is there; string or number, never parsed as a number (S13)
        } `json:"players"`
    } `json:"response"`
}
```

Unknown fields are ignored, and nothing else Steam returns (avatars, real name, country, server
address, `profileurl`) is decoded at all. A player whose `steamid` was not asked for is ignored.

**A pass** is one call with the SteamIDs of every connected person whose Mattermost account is active
(§2.13 step 2), never more than 100. A failed call changes nothing: the last good statuses stand until
`steamKeepGood`. A good answer replaces the statuses, writes back changed names (§2.6), and stamps
`fresh`. A person Steam leaves out of a good answer gets state `""` (not guessed) until an answer
includes them again.

**Failures.**

- **403**: Steam says the key is wrong ("Retrying will not help", S15). Reading stops until the
  settings change (`holding`); statuses are dropped; admins see "Steam refused the Web API key. Check
  it in the Steam section." Connecting still works (S11 just leaves the name empty).
- **429**: wait `steamSlowDown` (holding), and tell admins at once.
- **Anything else** (5xx, network, a body that will not decode, a 400): back off `steamBackoff`, and
  tell admins after three failed passes, as Twitch does.

### 3.6 What is kept, and what never is

| Kept | Where | How long |
|---|---|---|
| SteamID64 (string), Steam name, when connected | `steam_links` | until Disconnect, an admin's removal or Delete all |
| Online state and game name | the loop's memory | until the next pass; dropped 5 min after the last good one, on Disconnect, on a switch-off, on deactivation (and never asked for a deactivated or deleted Mattermost account) |
| Response nonces (hashed) | `steam_nonce_…` | 10 minutes |

Never stored or forwarded: a password (VillaNET never sees one: Steam's page takes it), any Steam
session or cookie, avatars, `realname`, `loccountrycode` and the other location fields,
`gameserverip`, `timecreated`, `primaryclanid`, `lastlogoff`, a game history, playtime.

### 3.7 What is shown, and to whom

To **linked and let-in readers only**, through `GET /api/v1/accounts` (§2.9):

| Steam says | `state` | `game` | Shown to others | Shown to the owner, in their Steam row |
|---|---|---|---|---|
| `communityvisibilitystate != 3` | `offline` | none | as offline | "Your Steam profile is private, so people here see you as offline." |
| `personastate` 0 | `offline` | none | as offline | Offline |
| 1, 5, 6 | `online` | — | Online | Online |
| 2 | `busy` | — | Busy | Busy |
| 3, 4 | `away` | — | Away | Away |
| any other value | `offline` | none | as offline | Offline |
| public, `gameextrainfo` set | as above | the name, cleaned, at most 80 runes | **Playing {game}** | Playing {game} |
| public, `gameid` present, `gameextrainfo` empty | as above | `""` with `inGame: true` | In a game | In a game |

- Private profiles never show a game, whatever `personastate` says (S11's 5/6 bug included).
- "Offline" is never drawn for others **in the panel** (the strip shows only people playing); the
  popover's Steam row dims for an offline person (§5.4).
- The profile link is `https://steamcommunity.com/profiles/<SteamID64>`, built on the server, opened
  with `target="_blank" rel="noopener noreferrer"`, never `nofollow` (S14 §3). Pressing it is an
  ordinary outbound link, like **Watch on Twitch ↗**.
- **No Steam avatar and no game art**: both are on Steam's CDNs, and the media relay's rule ("only
  titles a panel shows") is not widened for this. Mattermost's own avatars are used everywhere.

### 3.9 Security

- Starting a Steam sign-in needs a ticket only the panel can get by a CSRF-protected POST, bound to the
  session; without one the connect page writes nothing, counts nothing and goes nowhere (C1-C6).
- Linking someone else's Steam account to yourself, or yours to someone else, is refused three ways:
  the callback needs the starter's own interactive session (K6), Steam's signature covers our state
  (S6), and a state started by Matty can never be finished by a browser (K5).
- The verification is xPaw's strict list (S8), with the server and the callback hard-coded (S9), no
  discovery, no Host header, and no repeated parameters (S2).
- The Web API key is sent only to `api.steampowered.com`, in a header (S15, S19), never logged, never
  sent to a browser or Matty, masked in the console, left out of backups.
- Every SteamID is parsed by pattern and kept as a string; every name and game is `cleanText`ed and
  length-capped before it is stored or shown; React escapes everything drawn.

### 3.10 Privacy, and Steam's terms (S14)

- **"Only as requested by the end user"**: Steam data is read only about people who connected their
  own account, only while they are connected and their Mattermost account is active (a deactivated or
  deleted account is never asked about, §2.13); Disconnect stops it at once.
- **Tell users what is stored; post a privacy policy; name the country**: the consent note (§5.3), the
  README's privacy notice (§7.2) and, once Victor answers Q5, the country the server is in.
- **"As is"**: the README says Steam's information is shown as Steam gives it, with no promise from
  Valve or this server that it is right or current (§7.2).
- **Not endorsed by Valve**: the help text, the card and the README say so.
- **Keep the key confidential**: §3.9.
- **Delete on ending** (Steam's terms §11: ending includes "deleting all copies of the Steam Data"): Disconnect, an
  admin's removal, and Delete all Steam data delete everything, takeover notices naming the account
  included (§2.6); whether switching Steam off should also delete everything is Q7 (default: kept, as
  Twitch's are). Removing the plugin does not delete the plugin's data, so the README, LOCKDOWN and the
  card's item 7 tell the admin to press Delete all Steam data first when removing the plugin for good
  or stopping use of the Web API.
- **What the server's own proxy keeps**: on the web, Steam's return is a GET whose query carries the
  person's SteamID twice (`openid.claimed_id`, `openid.identity`, S8), and a reverse proxy's access log
  records the whole address (M10, X1). VillaNET cannot delete that; the privacy notice says so, and
  LOCKDOWN tells the admin how to log that path without its query (§7.2, §7.3). Matty's window never
  loads the return (§6.5), so it is not affected; Hytale's return carries only `code`, `state` and
  `scope`.
- **Not to third parties**: nothing goes anywhere but this server's panels and Matty.

### 3.11 Risks

| Risk | What the build does |
|---|---|
| Steam's endpoint rate-limits `check_authentication` (S8) | The `busy` page; nothing is half-written (the nonce record expires). |
| Steam changes its signed list, or its claimed-id form | Connects fail closed with reason `signed` or `identity`, logged once; a one-line fix. |
| Akamai caching makes statuses lag (UNVERIFIED how much) | 60 s is a ceiling, not a promise; the README says "within a minute or two". |
| A private profile with public game details, or the reverse | Only `communityvisibilitystate == 3` shows anything; the owner's row says how to change it. |
| The Steam app on Android takes over steamcommunity.com links (S18) | Matty's own sign-in window is a WebView, which apps cannot take over (§6.5); a Custom Tab is never used for connecting. |
| A shortcut's `gameid` past 2^63 (S13) | Never parsed; only its presence is read. |
| Steam's Terms change | The README links them; Delete all is one press. |

## 4. Hytale (part C)

### 4.1 What it is, and what it cannot be

A linked person presses **Connect Hytale**, signs in on Hytale's own page, picks a game profile, and
comes back connected. From then on, everyone who can open the panel sees that profile's **username**,
with a Copy button, so friends can find each other in-game.

**There is no Hytale status and no location**, and every word in VillaNET says so. Hytale's
third-party sign-in returns identity only (H9); its planned first-party APIs have no presence,
online-status or location endpoint, and are for authenticated game servers anyway (H11); and Victor's
group plays on other people's public servers (his answer), so a server-side plugin is not available
either.

### 4.2 Setting it up

1. At `accounts.hytale.com`, **Third-party developer apps**, apply for an application (H13):
   - **Client type: confidential.**
   - **Redirect URI**, exactly: `<Site URL>/plugins/ceo.villa.villanet/api/v1/hytale/callback`
     (§0, already told to Victor). A lab on `http://localhost:8065` would need
     `http://localhost:8065/plugins/ceo.villa.villanet/api/v1/hytale/callback` as a second entry, if
     the portal allows several (UNVERIFIED, H14); otherwise the lab uses the fake only.
   - **Scopes: `openid` and `hytale:profile`.** Only granted scopes may be asked for (H5), and VillaNET
     asks for exactly these two, never `offline`, `offline_access` or `account:*`.
   - Hytale's staff review it (H13).
2. Paste the Client ID and Client Secret; switch on **Show people's Hytale names**.
3. Read Hytale's developer terms in the portal (they are not public, H13) and tell us of any rule
   about showing usernames or keeping them (B0 in §9.2).

`hytaleCallbackURL(siteURL)` follows the same rules as Steam's with Hytale's words ("Hytale needs an
https:// Redirect URI, and the Site URL is http://…"), and is `strings.TrimRight(siteURL, "/") +
"/plugins/ceo.villa.villanet/api/v1/hytale/callback"`, used **byte for byte** for the authorize
request and the exchange (H14). `hytaleProvider.setup` is that problem, "Fill in the Client ID and
Client Secret above first.", the shape sentence (§2.10), or "".

### 4.3 Start: `hytaleStart`

- `st.Return = hytaleCallbackURL`; `st.Nonce = randomHex(32)`; `st.Verifier` = base64url (no padding)
  of 32 random bytes, 43 characters (H8).
- `code_challenge = base64url(sha256(st.Verifier))`, no padding.
- The location is `hytaleBase + "/oauth2/auth?"` with these parameters **in this order**, each escaped
  with `url.QueryEscape` and then `+` replaced by `%20`, so the scope's space is `%20`:

| # | Name | Value |
|---|---|---|
| 1 | `response_type` | `code` |
| 2 | `client_id` | `HytaleClientID` |
| 3 | `redirect_uri` | `st.Return` |
| 4 | `scope` | `openid hytale:profile` |
| 5 | `state` | the state |
| 6 | `nonce` | `st.Nonce` |
| 7 | `code_challenge` | the challenge |
| 8 | `code_challenge_method` | `S256` |

No `prompt` (Hytale asks every time, H9), no `response_mode` (the default for `code` is `query`, a
GET, which both the browser's session cookie and Matty's window need). `hytaleBase` is
`https://connect.accounts.hytale.com`, the issuer of H1, a variable for tests. The second discovery
document (`oauth.accounts.hytale.com`, H2) is never used.

### 4.4 Finish: `hytaleFinish`

On the callback's 15 s budget. Steps Y1-Y2 make no outside request.

- Y1. `error` present (this is K8): `access_denied` is page `cancelled`; `invalid_scope` is page
  `scope`, and admins' `/me` problem says so; anything else is page `providererror`, logged only if it
  matches `^[a-z_]{1,40}$`, else `other`. `error_description` is never read.
- Y2. `code` absent, repeated, or longer than 512 bytes: page `expired`.
- Y3. **Exchange.** `POST hytaleBase + "/oauth2/token"`, `Content-Type:
  application/x-www-form-urlencoded`, `Accept: application/json`, `Authorization: Basic
  base64(url.QueryEscape(clientID) + ":" + url.QueryEscape(secret))` (H6, H7: **not** a bare
  `SetBasicAuth`), and the body exactly `grant_type=authorization_code`, `code`, `redirect_uri=st.Return`,
  `code_verifier=st.Verifier`: **no `client_id` and no `client_secret` in the body**. Through
  `sendMedia`. 401 `invalid_client`: page `providererror`, and admins' problem names the credentials.
  Any other non-200: page `providererror`, reason `status`. The answer, capped at 64 KiB, must have
  `access_token` (printable ASCII, no spaces, at most 4096 bytes), `id_token` (at most 8 KiB) and
  `token_type` `Bearer` (any case); a `refresh_token`, should one ever come, is never decoded.
- Y4. `defer` a revoke: `POST hytaleBase + "/oauth2/revoke"` with the same Basic header and
  `token=<access_token>&token_type_hint=access_token`, on a fresh 8 s context, best effort, warned
  once on failure. It runs whatever happens next.
- Y5. **The ID token**, by a new `checkHytaleIDToken(raw, clientID, nonce, now)` beside Twitch's
  (Twitch's `checkIDToken` is not touched): at most 8 KiB, three parts, base64url JSON; `iss ==
  "https://connect.accounts.hytale.com"`; `aud` the client id as a string or a one-element array;
  `exp` an integer after now minus 5 minutes; `nonce == st.Nonce` in constant time; `sub` a string of
  1 to 255 bytes, printable ASCII (no shape is assumed: Hytale documents none, H16, and a guessed
  pattern would fail every connect closed). Refusals are fixed code words (`size`, `shape`, `iss`,
  `aud`, `exp`, `nonce`, `sub`), page `providererror`. **No signature check**: the token comes straight from the
  token endpoint over TLS (H10, the template's T19), and the code is bound to this state twice over,
  by the PKCE verifier held only on the server and by the nonce.
- Y6. **Userinfo.** `GET hytaleBase + "/userinfo"` with `Authorization: Bearer <access_token>` and
  `Accept: application/json`. 200 only; `Content-Type` must be JSON (a signed `application/jwt`
  answer is refused); capped at 64 KiB. `sub` must equal the ID token's `sub` (H10 §5.3.2), else page
  `providererror`, reason `sub`. No `profile` object: page `noprofile`. `profile.uuid` must match
  `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$` (kept lower case);
  `profile.username` must match `^[A-Za-z0-9_]{1,32}$`, deliberately looser than the 3-16 the guides
  report (H12), so a rule change by Hytale does not lock people out; else page `providererror`,
  reason `profile`.
- Y7. The proof: `{ID: uuid, Name: username}`. `sub` is dropped here: nothing needs it, and it is a
  per-application identifier (H9).

### 4.5 What is kept, and what never is

| Kept | Where | How long |
|---|---|---|
| The chosen profile's uuid and username, when connected | `hytale_links` | until Disconnect, an admin's removal or Delete all |
| The state's nonce and PKCE verifier | `hytale_state_…` | at most 10 minutes, spent at the callback |

Never: a password (Hytale's page takes it), any token, ID token or code, `sub`, an e-mail (Hytale has
none to give), the `account:*` booleans. **The uuid is the key**: one profile has at most one
Mattermost owner, and a verified proof of it wins a takeover (§2.6). One person keeps one profile;
connecting again (and picking another profile) replaces it.

**Names do not refresh.** VillaNET keeps no refresh token, so it cannot ask Hytale again; a profile
renamed in Hytale (at most once in 30 days, H12) shows the old name until its owner connects again.
The README and the sheet say so. Asking for `offline` would break the "never keep a token" promise.

### 4.8 Security

- The template's ticket, state, session and access checks (§2.5), plus **PKCE S256**: a code that
  leaks (in a proxy log, M10) is useless without the verifier, which never leaves the server.
- The client secret goes only to `connect.accounts.hytale.com`, in the Basic header, escaped as
  fosite expects (H6, H7); never in a body, a log, a page or a browser.
- The ID token's nonce, issuer, audience and expiry are checked; userinfo's `sub` must match it; the
  username and uuid are pattern-checked before they are stored; the token is revoked at once and never
  kept.
- Some errors (an unknown client, a mismatched redirect) are shown on Hytale's own page and never come
  back (H4). The panel's Waiting step says what to do after a minute (§5.3).

### 4.9 Privacy

Hytale's public terms say nothing about third-party apps (H13). The consent note says exactly who sees
what: everyone who can open the panel sees the username you pick; nothing else is known or shown.
Hytale's own sign-in page loads Cloudflare Turnstile and Hytale's Sentry, which records session
replays for a share of visits (H13), and, if the person accepts Hytale's cookies, Cloudflare's
analytics; its policy lets the page talk to any https host and send its sign-in form to Google,
Microsoft, Discord, Twitch and Epic Games, which suggests it offers signing in with them (H15). That
is Hytale's page, and the README, LOCKDOWN and the help text say so, naming hosts as examples, not a
complete list.

### 4.10 Risks

| Risk | What the build does |
|---|---|
| Hytale has not granted `hytale:profile` (H5) | Every connect fails at Hytale with `invalid_scope`; the `scope` page and the admin problem say exactly that. |
| Hytale moves endpoints or changes the issuer (H2) | `hytaleBase` and the issuer are one constant each; connects fail closed (`iss`), logged once. |
| The portal allows one Redirect URI only (UNVERIFIED) | The lab uses the fake; the real server is the one entry. |
| The signed-in account has no game profile (UNVERIFIED what Hytale does) | `noprofile` page if userinfo has no `profile`; `providererror` if Hytale errors. |
| A Basic-auth escaping mistake | `TestHytaleExchangeUsesEscapedBasicAndNothingInTheBody` with a secret holding `+`, `%`, `:` and a space. |
| Hytale renames | Shown stale until reconnect; stated. |
| A pending community library is the only evidence for Basic and PKCE (H6, H8: PR #1499 is unmerged) | The fake asserts both; §10.2 V-checks run against the real Hytale before the release note says it works. |

### 5.7 The accounts store (`webapp/src/accounts.ts`)

- **Signing out drops it** (the 3.1.0 rule): `followSignIn`'s sign-out callback and `uninitialize`
  clear the store with a generation counter, so a request in flight cannot refill it.
  `build/check-away.mjs` gains the case.
- `index.tsx` registers `custom_ceo.villa.villanet_accounts` and

- `client.ts`: `fetchAccounts()`, `fetchAccountTicket(service)`, `accountConnectURL(service, ticket)`,
  `unlinkAccount(service)`, `dismissAccountNotice(service)`, and the admin calls. All through
  `baseHeaders` (X-Requested-With and the CSRF token).

## 6. For Matty (part E): the API a native app uses

This section is the contract a later Matty change codes against. The README carries the same, as
**"Native apps (Matty)"** (§7.2). Nothing here needs Matty to change to keep working: every addition
is a new field, route or event, which today's Matty ignores (A2, A4).

### 6.1 Ground rules

- **Base**: `<Site URL>/plugins/ceo.villa.villanet/api/v1`.
- **Every request**: `Authorization: Bearer <session token>` and `X-Requested-With: XMLHttpRequest`.
  A Bearer request needs no CSRF token (M1). Never put the token in a query string.
- **Sessions**: anything that **adds** a connection needs an interactive session: a password or single
  sign-on sign-in. A personal access token is refused with code `interactive_only` (M3, V6). Reading
  and disconnecting work with any session.
- **Answers** are JSON, never a redirect (Matty's client follows none, A1), with `Cache-Control:
  no-store`. A refusal is any non-2xx with `{"error": "<a sentence a person can read>", "code":
  "<a stable word>"}`; Matty may show `error` or word the code itself.
- **Compatibility**: fields are only ever added. No field Matty decodes today (A3) changes, and
  `twitch`, `twitch_link` and `streams` keep their shapes.
- **Access**: `GET /me` tells the app who the reader is (`access`: `linked`, `letIn`, `locked`). Ask
  `GET /accounts` only when `access` is `linked` or `letIn`; a locked reader gets 403 `locked`, and
  must be shown nothing about anybody's Steam or Hytale, in the profile sheet included (Victor's
  answer; Matty's `ProfileExtras` checks no access today, A6, so the later change must).

### 6.2 Every route

| Method and path | Class | Body | Answer | Refusal codes |
|---|---|---|---|---|
| `GET /me` | open | — | 3.3.0's fields, plus `steam` and `hytale` (§6.4) | `store` |
| `GET /accounts` | watch | — | §6.4: everyone's Steam status and Hytale names, one request for all | `locked` (let-in readers may read it; it is served from memory, so there is no `store`) |
| `POST /steam/app-connect`, `POST /hytale/app-connect` | linked | `{}` | `{"url", "finishAt", "expiresIn"}` | `locked`, `watch_only`, `interactive_only`, `off`, `setup`, `blocked`, `full`, `rate_limited`, `store` |
| `POST /steam/app-finish`, `POST /hytale/app-finish` | linked | `{"query": "<the raw query of the intercepted address>"}` | `{"ok": true, "account": <MeAccount>}` | `locked`, `watch_only`, `interactive_only`, `bad_request`, `expired`, `other_session`, `cancelled`, `provider_error`, `busy`, `scope`, `no_profile`, `off`, `blocked`, `full`, `store` |
| `DELETE /steam/link`, `DELETE /hytale/link` | open | — | `{"ok": true}` (also when nothing was connected) | `store` |

### 6.4 The JSON

`/me` additions (`MeAccount`, the same shape for both; absent means the service is off and the reader
has nothing there):

"steam":  {"available": true, "connected": true, "name": "Dave",
           "url": "https://steamcommunity.com/profiles/76561197960287930", "hidden": false},
"hytale": {"available": true, "connected": true, "name": "Steve_Hytale"}

`GET /accounts` (§2.9), for a profile sheet, a member list and avatars from memory: one request
whatever the number of people. Rejected shapes: a per-person route (a request per profile, and one per
row of a member list); fields on `/streams` or the `streams` event (they reach locked readers, V14);
fields on `/me` (everybody's data in a per-caller answer); an `?ids=` batch like `clips/cards` (only
worth it past a few hundred people, and the cap is 100 a service).

```jsonc
{"v": "3f2a9c01b7de",
 "steam":  {"on": true, "fresh": true, "at": 1794430000000},

   "<mmUserId>": {"steam":  {"name": "Dave", "url": "https://steamcommunity.com/profiles/76561197960287930",

```

### 6.5 Connecting from Matty: its own sign-in window (default, Q1)

**On the server.** `POST /api/v1/{p}/app-connect` (linked), in order:

- AC1. `no-store`. Not interactive: 403 `interactive_only`.
- AC2. Off: 404 `off`. Setup problem: 503 `setup`.
- AC3. Links unreadable: 503 `store`. Blocked: 403 `blocked`. Not connected and at the cap: 409 `full`.
- AC4. The service's connect limiter (the ticket's): 429 `rate_limited`.
- AC5. `state = randomHex(32)`; `st = {Provider, User, Session: c.SessionId, At, Mode: "app"}`;
  `location := p.start(…)`.
- AC6. `KVSetWithExpiry(p.id+"_state_"+state, st, 600)`: 503 `store` on failure.
- AC7. 200 `{"url": location, "finishAt": <callback without query>, "expiresIn": 600}`.

No ticket: a ticket exists to protect a GET that a page, an image or a frame could fire with the
reader's cookie (`twitch-live.md` §4.2). There is no such GET here: the state is made by a Bearer POST
that only the session's holder can send.

`POST /api/v1/{p}/app-finish` (linked), body at most 8 KiB, in order:

- AF1. `no-store`. Not interactive: 403 `interactive_only`. Body or `url.ParseQuery(query)` fails:
  400 `bad_request`.
- AF2-AF4. K2-K4 on the parsed query: the state's shape, its record, its provider and age, spent
  (400 `expired`, 503 `store`).
- AF5. **`st.Mode == "app"`, `st.User ==` the caller and `st.Session == c.SessionId`** (constant time),
  else 403 `other_session`. A state made by the web flow can never be finished here, and a state made
  by one session can never be finished by another.
- AF6. `accessOf` again: 403 `locked` or `watch_only`.
- AF7-AF10. K8-K11 with the same `p.finish`: the same Steam checks (§3.4) and Hytale exchange (§4.4),
  each refusal a code.
- AF11. K12, then 200 `{"ok": true, "account": <MeAccount>}`.

**In Matty** (later Matty work, copying its GitLab sign-in, A8):

1. `POST /{p}/app-connect` → `url`, `finishAt`.
2. Open `url` in a **sign-in window** (a WebView screen): https only, certificate errors refused, no
   file or content access, no mixed content, no JavaScript interface, no multiple windows, the current
   host shown in the top bar (the person sees `steamcommunity.com` or `accounts.hytale.com`). Plain
   `loadUrl(url)` with **no headers**: no Mattermost token or cookie is ever in this window.
3. Watch every main-frame navigation in `shouldOverrideUrlLoading` and, because that is not called for
   a navigation started by a POST (A9), in `shouldInterceptRequest` too: an address whose scheme, host,
   port and path equal `finishAt` exactly is **never loaded** (return `true`, or an empty response).
   Take its raw query, close the window, and wipe the window's cookies and storage.
4. `POST /{p}/app-finish {"query": "<raw query>"}` → the account, or a code to word.
5. If the person closes the window, do nothing: the state expires in ten minutes.

**Why this keeps the template's account-linking defence.** Somebody who calls `app-connect` with their
own token and sends the sign-in address to somebody else gets nothing: that person's browser signs in,
is sent to the callback, and the callback (K5) spends the "app" state and links nothing, leaving the
assertion or code in the victim's browser and the state gone, so the sender's `app-finish` finds
nothing (AF2-AF4). Nobody can finish anybody else's state (AF5). The Steam assertion or Hytale code
is checked by the server exactly as on the web. And because Matty never loads the return address, the
code never reaches the server as a GET, so it never lands in the reverse proxy's access log (M10).

**What Victor registers for Matty: nothing more.** Steam needs nothing; Hytale's one Redirect URI is
the same https callback, which Matty catches rather than loads, so the client secret and the PKCE
verifier stay on the server and no custom scheme or public client is needed.

UNVERIFIED, and checked on a real phone before Matty relies on it (§10.2): that Steam's and Hytale's
sign-in pages work in an Android WebView (Hytale's Turnstile check, H13; any Google or Apple sign-in on
Hytale's page would refuse a WebView), and that the interception sees the return in both.

### 6.6 Why not a callback that needs no session

The task suggested letting Matty POST for a ticket with its Bearer token, open the connect address
carrying the ticket in the phone's browser, and have the callback stop requiring the Mattermost
session, relying on the ticket being bound to the user, single use and short-lived. **That is not
safe**, and this contract does not build it:

1. A browser opened from Matty carries no Mattermost session (A7), so the connect page could no longer
   compare the ticket's session with the browser's (C5). The ticket in the address becomes the only
   proof, and an address can be passed on.
2. Attacker A asks for a ticket with A's own token and posts the connect link, an address on
   VillaNET's own server, in a channel or a message.
3. V opens it in a browser with no Mattermost session (usual on a phone, and in a desktop-app user's
   default browser). The connect page spends A's ticket **in V's browser** (any "binding" cookie it
   sets lands in V's browser too) and sends V to Steam, where V is already signed in and presses
   **Sign in**.
4. The callback, needing no session, links **V's Steam account to A's Mattermost account**. Everyone
   in the panel then sees V's online state and games under A's name, which V never agreed to (the very
   thing Steam's terms forbid, S14, and the attack the template's K6 exists to stop).

Being bound to A, used once and inside its ten minutes describes exactly this ticket. What would make a
browser-based Matty flow safe is proof that the browser that finishes is on the device that started,
which needs a way back into Matty (a claimed link), and Matty has none (A7). So the web callback keeps
requiring the starter's own session (K6), and Matty finishes inside Matty (§6.5).

### 6.7 Events, and when to read

| Event (after Matty's prefix stripping) | Payload | Do |
|---|---|---|
| `accounts` | `{}` | If `access` is `linked` or `letIn` and a VillaNET screen or a profile is visible, `GET /accounts` (at most once a second); otherwise mark it stale and read on the next show. |
| `account_link` | `{}` | `GET /me` (the reader's own Steam or Hytale changed: connected, disconnected, blocked, taken over). |
| `access`, `twitch_link`, `streams` | as today | as today |

`accounts` goes to everybody; it says only "something changed". A phone in the background need not
read on it: Matty's own rule is to read only while its UI is visible (`docs/PLUGINS.md`), and a
foreground read catches up.

## 12. Limits and out of scope

- **Hytale status or location**: impossible with Hytale's third-party sign-in (H9, H11), and Victor's
  group plays on other people's servers. A Hytale server plugin on a server Victor runs could report
  presence; not asked, not designed.
- **Steam friends lists, achievements, playtime, avatars, game art**: not asked; most would be stored
  Steam data with its own deletion duties.
- **Folding Twitch onto the accounts core**: a later release.
- **Matty itself**: §6.8 is the later work, with previews first.
- **A Mattermost cluster**: each node runs the loop, so Steam calls multiply by the number of nodes
  (at three nodes, 4,320 a day, still far under 100,000), and a link write rebuilds the view only on
  the node that served it; the others catch up at their next minute's step (§2.13). Nothing else is
  designed for a cluster: the single-server assumption is the airtime tables' too.
- **Fresh Hytale names**: none without refresh tokens, which VillaNET will not keep.
- **Steam and Hytale logos**: not used; their brand rules were not read for this. The words "Steam"
  and "Hytale" are used plainly.
- **Notifications** ("Dave started playing"): not asked.
