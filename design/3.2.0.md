**Status.** Design only: nothing here is built. 3.1.0 is built and unreleased, tested in the lab and
by tests only (`design/STATUS.md`). Victor wants to see the options before any visible UI is built,
so the build starts with a preview (§12.1, phase P), and the questions in §14 go to him with it. Until
he answers, the build uses each question's default.

**Victor's standing rules, binding on every part of this document:**

- The panel is locked until a person unlocks it with their own bearer token, which links their
  Broadcast Box stream ("linked"). A system admin can let people in to **watch only**. Interactive
  features are for linked people only, and the server enforces it (`server/access.go`
  `routeClasses`, `accessOf`).
- Votes count only while the voter is linked.
- Shares post as the sharer, with a custom card, into the current channel, with no title or names in
  the message text.
- Browsers contact nobody but the Mattermost server. Twitch's player and Connect are the stated
  exceptions, and nothing here adds one.
- Stream keys, bearer tokens and secrets are never logged and never sent to browsers.
- The settings backup leaves secrets out unless ticked.
- Preview (screenshots of the options) before any visible UI is built.
- Calm, minimal, modern UI matching the plugin: black, the emblem, Oswald capitals, the plugin red,
  and the one quiet footer bar whose small tools open sheets that rise from the bar, one at a time.
- The lock screen shows nothing but the emblem, the bar and status. It does not advertise being let
  in and shows no admin lines. **Nothing in 3.2.0 adds anything to the lock screen.**
- Only Mattermost 11.11 is supported.
- Mattermost and library behaviour is verified in real source, never from memory.

**How this relates to the other contracts.**

- `design/lock-screen.md`: every new route gets a class (§2.2). "Outside the panel nothing is hidden"
  covers the new badges, fan titles and achievements, which ride the open snapshot like the medals.
  Let-in people get nothing interactive from 3.2.0: no picker, no soundboard, no share, no vote. The
  only new things anybody not linked can press are takebacks (stop being counted as a fan, delete your
  own sounds), offered in their own profile popover, outside the panel (§4.6).
- `design/clips-spec.md` with `design/clips-addendum.md`: the plan share card is built on the clip
  share card's pattern (`server/clips_share.go`), and its two hooks are generalised rather than
  copied (§6.4). The addendum decided that a shared clip's card shows no upvotes (`clips-addendum.md:790`);
  Victor's item 8 reverses that for readers who may see clips. Review fix #3 there (every vote changes
  `clips.version`, so following it naively makes every client refetch every card,
  `clips-addendum.md:1074`) stays fixed: §9.4 follows the version only for cards on screen, batched
  and throttled.
- `design/twitch-live.md`: Twitch hours stay deletable. Achievements are worked out live (§5.2), so
  nothing derived from Twitch hours outlives a disconnect. Twitch cards get no @names (Twitch titles
  use @ for Twitch handles) and no fans (Twitch has no sessions VillaNET can see).
- `design/media-lookups.md`: a plan card's art uses the existing open picture route and its
  `refShownHere` rule unchanged.

### 2.2 New routes and their classes

`TestEveryRouteHasAnAccessClass`. Every non-GET goes through Mattermost's CSRF check like the existing

### 3.1 What can be chosen

they hold none.

| `month` | This month's airtime place | Their row on `snapshot.month` has rank 1-3 | `MonthBadge` (calendar) |

### 3.2 Automatic, and a choice

- **Automatic** (never chosen, or chosen back): exactly 3.1.0. The four old awards, `alltime`,
  `month`, `snooper`, `clipper`, whenever held, in that order. **Nothing new ever appears beside a name
  automatically**: past-month medals, fan titles and achievements show there only when their owner
  chooses them. That
  keeps "nobody chose" byte-for-byte what 3.1.0 draws, and keeps awards rare beside names, which is
  their point (`AwardBadges.tsx` header comment).
- **My choice**: an ordered list of **up to four** ids. Four is the most 3.1.0 can draw (crown,
  calendar, binoculars, clapper), so with the headphones a header is never wider than today: five icons
  at 16 px with 3 px gaps, about 92 px.
  - An id the person does not hold now is **skipped and kept**: win the month again and the calendar
    comes back where they put it.
  - A newly won award **waits** until they add it. The You tab marks it "New" (§3.6).
  - An empty list is a choice: nothing beside the name but the headphones.

One pure function decides it everywhere, `shownAwards(held, choice)` in `webapp/src/awardLogic.ts`
(imports nothing): `choice` is `null` for Automatic.

### 3.3 Data: `award_prefs`

One KV document (§2.1), shaped like `now_playing`:

```json
{"v":1,"entries":{
  "u1…26":{"show":["month","fan:u2…26","ach:streamed"],"at":1760300000000},
  "u3…26":{"show":[],"at":1760300100000}}}
```

- `show` absent: Automatic, and the entry is removed. `show` present (possibly `[]`): their choice, in
  order.
- **No opt-out lives here.** The fan opt-outs are their own document, `fan_optouts` (§4.6), so that
  losing this one can only put badges back to Automatic, never re-enrol somebody who opted out.
- At most 500 entries (`maxAwardPrefs`). Only linked people write here (clearing is open, but clearing
  removes an entry), so the bound is reached only by 500 linked people; a new person past it is refused
  with "There is no room for another choice just now." and an admin warning in the log.
- Written only by `casUpdate` (8 attempts, replay-safe apply, `nil` old value to create), then
  `refreshSoon()`. The apply re-validates.
- **Bad bytes.** The document is copied once to `quarantine_award_prefs` and read as **nobody chose**:
  the badges fall back to Automatic. The next write starts a fresh document, and an admin log line
  says so. The You tab shows "Your choices could not be read just now, so your awards show
  automatically."
- **In memory.** Read at activation, after this node writes it, and by the poller when its copy is more
  than 60 s old; another node's write shows within a minute (single-server is the realistic target,
  as for airtime). The golden scene's list of keys read gains `award_prefs` and `fan_optouts` (read
  by the same rules) on its first poll only.

### 3.4 Server

`server/awards.go` (new):

- `GET /api/v1/awards/mine` (linked) answers `{"show": [...] | null, "fanNamed": true|false,
  "readable": true|false, "fansReadable": true|false}` for the caller, from memory.
  `Cache-Control: no-store`.
- `POST /api/v1/awards/display` (linked) takes `{"show": [...] | null}`, body at most 2 KB. Refused

  included); a `fan:`
  id whose rest is not 26 lower-case alphanumerics; an `ach:` id not in the current catalogue (§5.1).
  Whether the person holds it is **not** checked (they may choose ahead; it is skipped until held).
  `null` stores Automatic.
- `DELETE /api/v1/awards/display` (open) is "back to Automatic" for anybody, linked or not.
- All three share `awardLimiter` (10 a minute per person) and end in `refreshSoon()`.
- **Snapshot.** `addAwardChoices(current)` puts `awardChoices` on every snapshot: one row per entry with

## 4. Feature 2: the biggest fan

### 4.1 What it is

For each **linked streamer** (a person, through a manual link: `boardOwner`, V24), their biggest fan is
the **linked viewer** who has spent the most time watching that streamer's Broadcast Box streams in the
panel, **all time**, provided it is at least **one hour** (`minFanSeconds = 3600`). Victor's words: the
streamer's "most watched snooper".

- **Who counts** is exactly who Top Snoopers counts (V9): linked viewers only, both link entries
  agreeing; never let-in or locked people; never their own stream; never a paused stream; never peeks
  or the recorder; never Twitch (no sessions), and **never 24/7 channels**, which have no person to be
  a fan of (§5.5 counts them separately, for achievements).
- **Not counted at all** while Top Snoopers (`TopWatchers`) or `EnableBiggestFans` is off, or for a
  viewer who opted out (§4.6), or while `fan_optouts` cannot be read (then nothing is shown either).
- **Two streams at once** credit both streamers their own clock time: a viewer with Dave and Bob open
  for an hour is an hour of fan time for each. Top Snoopers still pays them one hour. Stated in the
  README, because the per-streamer figures then add up to more than the viewer's snooper total.
- **Ties** at the top keep the current holder (as Best Clipper does, V13), known from the snapshot
  before; with no holder (a restart), the lower user id.
- **No backfill.** Nothing ever recorded who watched whom (V9), so everybody starts at zero on the day
  3.2.0 is installed. The README and the Snoopers tab say so ("Counted since 3.2.0").

### 4.2 Data: `fans_totals`

A `statTable` (§2.1) keyed `"<streamerUserId>:<viewerUserId>"` (Mattermost ids are 26 lower-case
alphanumerics, so `:` cannot occur in either), `title` always `""`, written by `saveStats`. **All time
only**: no monthly tables in 3.2.0 (Q1 offers "this month too", which doubles the writes). At most 2000
rows (`maxTrackedFanPairs`); a new pair past that is not counted, in a fixed order, with one log warning
per pass.

**Bad bytes: started again, not kept.** It is read by a new `loadLedger(key)`, not `loadStats`. A
store error is an error, as ever (the pass skips the table, §4.3). Bytes that will not decode are
**deleted** and the table starts from zero: no quarantine copy, no halt, no button. An Error log line
names the key and the byte count, and `/me`'s admin-only `ledgerAlert.fansResetAt` says so until the
plugin next restarts (§2.3, words in §4.7). Why, against `loadStats`' rule:

- It is who-watched-whom. A copy that cannot be decoded cannot have an opted-out person's rows taken
  out, and `quarantine` keeps its first copy for ever (V30), so a kept copy would break "the opt-out
  deletes what was counted". 3.1.0's Delete all Twitch data deletes its quarantine copies for the same
  reason.
- Losing it costs fan titles that start counting again; no board, medal or airtime depends on it. A
  halt and a restart button (and their route, status and words) would be machinery for that.
- 3.1.0 already treats `stats_sessions` this way (`loadSessions`, V30).

A downgrade to a VillaNET that cannot read a newer format would start it from zero too; the README says
so.

### 4.3 Counting: in the watch pass

`watchingNow` (V9) returns two more maps beside today's, built in the same loop from the same
audiences: `pairs map[streamerID]map[viewerID]time.Time` (the earliest `since` per pair, with one extra
test, `owner := boardOwner(*stream); owner != "" && owner != userID`) and `channels` (§5.5).
`recordWatchTime` keeps one clock for all three ledgers (`from`, `watchCreditLimit`, the first-pass
rule, `watchPollAt`) and takes this shape, under `statsWriteLock` as now:

1. The clock rules exactly as today. Then, if `watching`, `pairs` and `channels` are all empty **and no
   purge is pending** (§4.6), it is a quiet pass: no I/O, `watchPollAt` advances.
2. **Top Snoopers** (skipped when `watching` is empty or `watchHalt` is set): exactly today's code. A
   failed read or save still returns **without** marking the pass done, so nothing else is paid this
   pass and the next one pays the stretch to all three ledgers (today's "cheaper mistake").
3. **Fans** (skipped when fans are off or `fan_optouts` cannot be read; otherwise run when `pairs` is
   not empty **or** a purge is pending): drop every opted-out viewer from `pairs`; `loadLedger`
   (`fans_totals`); take out every row of every opted-out viewer (which is how a pending purge
   finishes); credit each pair from `max(from, ceilSecond(since))` to `now` with `credit`, in sorted key
   order; save. Once the save has succeeded, the purged viewers come off `fan_optouts.purge`
   (`casUpdate`). A failed load or save is logged ("Could not save the fan hours; this pass's are
   lost") and the pass **carries on**: the fan table never makes Top Snoopers pay a pass twice, can lose
   at most one pass (75 s at the default interval), and a pending purge stays pending.
4. **24/7 channel hours** (§5.5), the same way with `chanwatch_totals`.
5. `watchPollAt` advances.

A halted Top Snoopers ledger no longer stops the other two, and neither of them can stop it.

### 4.4 Display

`addFans(current, cfg, now)`, called beside `addWatchBoards`:

- **Faces on:** the table as the last credit pass saved it (kept in memory by that pass), or one read
  when this process has none yet.
- **Faces off:** the table as it stood at the first poll of the UTC hour, exactly like
  `watchTablesShown` (V10), so the figures move once an hour.
- Rows whose streamer or viewer is not linked now (`linkedNow`) are skipped, as are opted-out viewers
  and deactivated accounts (`resolve.person` nil). Grouped by streamer; the top row of each group with
  at least `minFanSeconds` wins, by the tie rule. Names resolved now (`displayNameOf`).
- `current.Fans` sorted by streamer id; `current.FansOn = cfg.EnableBiggestFans && cfg.TopWatchers &&
  optoutsReadable`. Both absent when off, or while `fan_optouts` cannot be read (fail closed: an
  opt-out that cannot be read must not be ignored). Carried by a failed poll like the watch boards.

### 4.6 Opting out

**Two places to say it.**

- In the You tab, under **BIGGEST FAN**, a switch (`role="switch"`), on by default:
  - Label: "Let VillaNET name me as somebody's biggest fan"
  - On: "Your time watching a streamer in the panel counts toward being their biggest fan."
  - Off: "You won't be named as anybody's biggest fan, and your watching isn't counted for it. What
    was counted has been deleted."
- In **your own** profile popover, through `registerPopoverUserActionsComponent` (M16: the slot is
  drawn in one's own popover too), for anybody signed in, linked or not, while `snapshot.fansOn` is
  set: an action **Don't name me as anybody's biggest fan** (or, once out, a quiet line "You're not
  counted for biggest fans." with **Let VillaNET count me again** for a linked reader). It reads its
  state from `GET /api/v1/takebacks` (open, `no-store`, no meter) when the popover opens. This is the
  way back for somebody who has **unlinked**: the You tab is for linked readers only, and the opt-out
  is open precisely for them. The popover is outside the panel, so the lock screen gains nothing.
- The same popover carries **Delete my sounds** (§7.7) whenever `takebacks.sounds` is above 0, whether
  the soundboard is on or off, so somebody can take their sounds back even after an admin switched it
  off.
- `GET /api/v1/takebacks` answers from what the server holds in memory: `fan_optouts` (read at most
  once a minute, §2.1) and the `sounds` document (held in memory while the soundboard is on; while it
  is off, read at most once every 30 s for the whole server, never once per request). So a Markdown
  image pointing at it costs nothing per reader.

**`fan_optouts`** (§2.1), its own document, not part of `award_prefs` (so that losing one cannot
re-enrol anybody):

```json
{"v":1,"out":{"<userId>":{"at":1760300100000},"<userId2>":{"at":1760300200000,"unlinked":true}},
 "purge":["<userId>"]}
```

**`POST /api/v1/awards/fan`** `{"named": false | true}`:

- `{"named": true}` (back in) needs a link (403 `watch_only` / `locked`) and removes the entry.
- `{"named": false}` is **open** (a takeback), and cheap to repeat:
  1. Already out: answer `{"named": false}` and write nothing.
  2. Otherwise add the entry by `casUpdate`. A caller who is **not linked** at that moment is marked
     `"unlinked": true`, and such entries are bounded at **200** of the document's 1000; past that a
     not-linked caller is refused 503 `full`, "There is no room for that just now.", with an admin
     warning in the log. Linked callers are bounded only by the 1000 (linked people are few). So no
     number of locked accounts can stop a linked person opting out.
  3. Purge only when there is something to purge: when this node's last-saved `fans_totals` copy holds
     a row for the viewer, or this node holds no copy yet, the user id goes onto `purge` in the same
     write, and the rows are taken out by an immediate rewrite under `statsWriteLock`. If that rewrite
     fails, the id stays on `purge` and **every** pass applies it, even a pass with nobody watching
     (§4.3 steps 1 and 3), until a save succeeds. A locked account that was never counted therefore
     costs one small write once, and never a rewrite of `fans_totals` under the airtime lock.
- Meter: `awardLimiter`, 10 a minute per person.

**When `fan_optouts` cannot be read.** Copied once to `quarantine_fan_optouts` (it says only who opted
out). Biggest fans **stop**: no counting, no display, `fansOn` false. Never replaced automatically,
because a fresh document would count again everybody who opted out. `ledgerAlert.fansOff` tells
admins, and the Airtime card offers **Start biggest fans again** (`POST /api/v1/admin/fans/restart`),
with a second press and this line: "This deletes every biggest-fan hour and forgets who chose not to be
named, so everybody is counted again from now. The unreadable list is kept in the plugin's store as
quarantine_fan_optouts." It deletes `fans_totals`, writes an empty `fan_optouts`, and logs who pressed
it. Deleting the hours as well means nothing of an opted-out person survives the restart.

A streamer cannot hide their own biggest fan in 3.2.0 (out of scope, §15).

### 4.8 Privacy

This is the one real privacy change in 3.2.0, and Q1 puts it to Victor.

## 5. Feature 3: achievements

### 5.1 The catalogue

Fixed in code except the 24/7 channel families, which an admin defines (§5.5). The step is the
highest threshold reached.

| Kind id | Family (head) | Name of a step | Steps | Counted from | Needs |
|---|---|---|---|---|---|
| `streamed` | ON AIR | "Streamed {n} hours" | 10, 50, 100, 250, 500, 1000 | All-time airtime **by person**, exactly as the boards: `boardRows(stats_totals, twitchair_totals)`, before the 50-row cut, rows with a user only (V11) | **Track streamed hours and award medals** |
| `snooped` | SNOOPER | "Snooped {n} hours" | 10, 50, 100, 250, 500 | `watch_totals` as the boards are shown (`watchTablesShown`, hourly with faces off), linked now (V10) | **Rank the Top Snoopers** |

A family whose switch is off is left out of the catalogue and of everybody's achievements while it is
off, and comes back when it is on: nothing is lost, because nothing is stored for the built-in ones.
The whole feature follows `EnableAchievements`.

### 5.2 Live, not stored

Achievements are **worked out at every refresh** from the figures VillaNET already has in hand while
it builds the snapshot: the uncut `allTime` rows in `addBoards`, the watch table in `addWatchBoards`,
the medal tally, and the clipper scores that `clipsCAS` already computes (kept in memory beside the
holder). **No KV read is added for the four built-in families.**

- **Backdated:** the first refresh after 3.2.0 gives everybody every step their existing hours reach.
- **They can go back down** when the figure does: a Twitch disconnect purges Twitch hours, switching
  Twitch live off takes them off the boards, a relink to a new stream key leaves the old key's hours
  behind (as on the boards), an admin import or restore of airtime, a Best Clipper reset, or unlinking
  (which hides watch hours). This is what keeps "Twitch hours are deletable" true without new rules,
  and it matches the boards people already see. Q8 asks Victor whether he would rather keep them
  permanently once earned.
- Only people linked now appear, as on every board.

### 5.3 Snapshot

- `achievementKinds`: the catalogue in the table's order, only for families that are on, with the
  channel names as the admin wrote them. Stable.
- `achievements`: one row per linked person holding at least one step, sorted by user id, `have` in
  catalogue order, `tier` the number of steps reached. At most 500 rows.
- The per-person figures behind them (hours, months, thumbs) are kept in memory only, for §5.6, and
  swapped whole at each refresh.

### 5.4 Announcing

Nothing is posted, sent, or shown to anybody else. In the earner's own unlocked panel, a quiet toast
over the footer bar for 6 s, the panel's notice style: **New achievement: Streamed 100 hours**
(`role="status"`). The browser remembers the steps it has already announced per person
(`localStorage` `villanet.achSeen.<userId>`, every access wrapped in try/catch). The first time a
browser sees somebody's achievements it records them **silently**, so the backdated ones do not arrive
as a burst of toasts. Storage that does not work means no toasts, never repeated ones.

### 5.5 24/7 channel achievements: `ChannelAchievements` and `chanwatch_totals`

**The setting.** One line per channel, at most 8 lines:

```
villanet-watts = Alan Watts = 1, 10, 50, 100, 250
```

- The key must be one of **24/7 stream keys** (`AlwaysOnStreamKeys`), compared normalised; otherwise the
  line is skipped and `/me`'s admin-only `achievementsAlert` says "24/7 channel achievements, line 2:
  that key is not one of the 24/7 stream keys." Other faults get their own sentence: "needs a key, a
  name and the hours", "the name is too long (32 at most)", "the hours must go up, from 1 to 100000,
  at most 8 of them".
- The id is `ch-` and the first 12 hex of an HMAC of `"achievement\x00" + normalisedKey` under
  `handle_secret` (V24), so it is stable, never equals a stream handle, and reveals nothing about the
  key. **The key itself never leaves the server.**

**Counting.** In the same watch pass, with the same clock:

- `watchingNow`'s faces-on early `continue` (V9, `watchtime.go:211`) changes from "not countable" to
  "not countable **and not a channel with an achievement**", so those audiences are read.
- For an `AlwaysOn`, not-paused stream named in the setting, every linked viewer in its audience (the
  same link rules, never let-in) goes into a third map, `channels map[normalisedKey]map[viewerID]time.Time`.
  Their snooper and fan counting is unchanged (24/7 still counts for neither).
- With faces off, `handleWHEP` records sessions for linked people whenever Top Snoopers is on (V9), so
  channel watching is seen exactly when Top Snoopers is on, and only then.
- `chanwatch_totals`: key `"<normalisedKey>:<viewerUserId>"` (the user id is the last 26 characters,
  parsed from the right, so a key containing `:` still parses), server-side only, like `stats_totals`
  keys airtime by stream key. Credited and saved after the fan table (§4.3 step 4), by the fan
  table's rules: `loadLedger`, 2000 rows, a failed save losing only that pass, and bytes that will not
  decode deleted and started from zero with a log line and `ledgerAlert.channelsResetAt` (§4.2). No
  halt and no button.
- Shown from the copy the last credit pass saved, or hourly with faces off, as §4.4.
- **No daily cap** (Q11). The README says that a tile left open counts.
- **Starts at zero** on the day 3.2.0 is installed: 24/7 watching was never recorded (V23). The tab
  says "Counted since 3.2.0" beside each channel family.

### 5.6 Your own progress

## 6. Feature 4: share a plan to chat

### 6.1 What it is

A linked person shares a planned stream into the channel they are looking at. It arrives as a card,
posted as them, that everybody in the channel can read in their own time zone and press: **Join** to
stream in it too (today's Join, V17), **Watch** once it is live. Victor's "click to join" is read as
both, because VillaNET's Join already means "I'm streaming in this too", and most readers will want
to watch; Q7 asks him.

### 6.2 Who may do what

| | Locked | Let in | Linked |
|---|---|---|---|
| Share a plan | — | — | Any plan on the list, anybody's (plans are already public on the snapshot) |
| See the card | Yes, in full (plans are already shown to everybody in the profile popover) | Yes | Yes |
| **Join** on the card | Absent | Absent | Yes, by today's rules: not your own plan, room for 12, linked (server-enforced) |
| **In ✓** (leave) | Absent | Shown to somebody who joined while linked; leaving is open, as today | Yes |
| **Watch** on the card | Opens the lock, with the stream waiting (`openLock({kind:'stream', …})`) | Yes | Yes |

### 6.3 Server: `POST /api/v1/schedule/share`

`server/plan_share.go` (new). Body `{"id":"<16 hex>","channelId":"<26>"}`, at most 1 KB. In order:

1. `requireLinkedStream` (layer 2 behind the gate; codes `watch_only`, `locked`, 503 `store`).
2. Body checks: `id` is 16 lower-case hex, `channelId` 26 alphanumerics; 400 `bad_request`.
3. `mayShareAs(userID)` (refuses bots and gone accounts), as clips.
4. A **fresh** read of the schedule, `prune(readSchedule())`, never the snapshot: a plan cancelled a
   moment ago is not posted. Not there: 410 `gone`, "That plan isn't there any more."
5. `mayPostShareIn(userID, channelID, cfg)` (V14): exists, not archived, not shared, member,
   `create_post`, DM rules. Every refusal is 403 `cannot_post` with the clip share's words.
6. The repeat window (generalised from clips, key `{userID, "plan:"+id, channelID}`): the same share
   within 60 s answers the post already made.
7. `planShareLimiter` (10 per 10 minutes per person); refused with 429 `rate_limited`, "You've shared a
   lot just now. Try again in a few minutes." A refusal after this point refunds the token.
8. `postSharedPlan`: issue a pass (§6.4), then `p.API.CreatePost` with:
   - `UserId` the sharer, `ChannelId`, `RootId ""`, `Type "custom_villanet_plan"`;
   - `Message`, fixed: `"📅 VillaNET plan"`, then `"\nSee it: " + site + "/plug/ceo.villa.villanet/plan/" + id`
     when Mattermost's Site URL is set (`shareSiteURL`, the same once-only admin log when it is not).
     **Never the title, the time or any name.**
   - `Props`: **only** `villanet_plan_id`, `villanet_plan_starts_at` (number), and the pass in
     `villanet_share_nonce`. Never the title, the host, the category, the picked media, joiners, art
     ids, stream keys or anything per reader.
9. Answer `{"postId","channelId"}`, as clips.

`POST /api/v1/schedule` also answers the new plan's `id` (V17), so the plan sheet can offer "Share it"
right after saving.

**No post tracking, and nothing to take back.** Unlike clips, the server does not keep the ids of the
posts a plan was shared in: the card reads the plan from the snapshot every reader already has (§6.5),
so cancellations, edits, joiners and "live" show without touching any post (M11). Because the props
hold only an id and a time, a plan that is edited or cancelled leaves nothing of its title, host or
media in any post. The post belongs to the sharer, who may not be the host, so the host could not
take a title back from it; clips scrub a deleted clip's props for the same reason
(`server/clips_share.go:18-25`).

## 7. Features 5 and 6: the soundboard

### 7.1 What it is

While somebody linked is in Mumble, a small speaker appears at the end of the panel's **In voice** row
(§2.7; P1 shows a footer-bar tool beside it). It opens a sheet, rising from the footer bar like every
sheet, of square tiles, each an emoji (or one of the server's custom emoji) over a short name.
Pressing one plays that sound into the Mumble channel they are in. After their sound ends they wait a
few seconds before the next. While they are muted, deafened or not allowed to speak in Mumble, the
tiles are greyed out and do nothing, and the server refuses a press anyway. Anybody on the board can
add sounds from a file: pick it, trim it to a few seconds, pick an emoji, name it. The server holds the
whole of it to "in Mumble": the board, adding and renaming are refused to a linked person who is not
matched to a Mumble session at that moment (§7.7, §7.9).

### 7.2 The audio path, without cgo

VillaNET's server cannot encode Opus: gumble's codec needs cgo (U3), and the build has none. So the
**browser** makes the Opus and the **server** checks, keeps and sends it.

1. **In the browser, when a sound is added** (`webapp/src/soundEncode.ts`):
   1. The file (at most 4 MB, because `decodeAudioData` decodes it whole into memory) is decoded by
      `new OfflineAudioContext({numberOfChannels: 1, sampleRate: 48000, length})`'s `decodeAudioData`,
      which resamples to 48 kHz (W3); rendering it once downmixes to mono.
   2. The person trims it: 0.25 to 6 s, with 5 ms fades at both ends.
   3. Loudness (`webapp/src/loudness.ts`, BS.1770-4: K-weighting, 400 ms blocks with 75 % overlap, the
      −70 LUFS absolute and −10 LU relative gates) is measured and a gain applied to **−20 LUFS**
      integrated; a 5 ms look-ahead sample-peak limiter then holds it under −1 dBFS. Not
      `DynamicsCompressorNode`, whose behaviour differs between engines. A sound shorter than 400 ms is
      measured as one block padded with silence. **Only the browser runs BS.1770**; the server holds a
      cruder ceiling (step 2).
   4. WebCodecs `AudioEncoder` with `{codec:'opus', sampleRate:48000, numberOfChannels:1,
      bitrate:40000, bitrateMode:'constant', opus:{frameDuration:20000, complexity:10}}`, flushed.
      That is Mumble's own client default, 40 kbit/s in 20 ms frames (U8), and gives packets of 100
      bytes (W2). **Constant bitrate needs Chromium 119** (W1): the add flow is offered only when
      `AudioEncoder.isConfigSupported(cfg)` resolves `supported: true` **and** its `config.bitrateMode`
      is `'constant'`; a browser that would quietly encode at a variable bitrate makes packets up to
      165 bytes, which the server refuses. After encoding, every packet is checked to be 128 bytes or
      less and the encoder's count to be at most 301; if not, the flow stops with "This browser can't
      make sounds…" (§7.14) rather than uploading something that will be refused.
   5. Uploaded as JSON with the packets in one base64 blob (§7.8): about 40 KB for 6 s.
2. **On the server, at upload** (`server/sounds_check.go`): every packet is checked by length and TOC
   (one mono 20 ms frame, §7.8), then **decoded** with `github.com/pion/opus` v0.1.0 (U13), inside a
   function that recovers a panic (M17), to prove it is real Opus, and the decoded sound is held to a
   **loudness ceiling**: K-weighted (BS.1770's two filters, no gating) level of the whole sound and of
   every 400 ms window (§7.8). An honest panel never trips it (the margins are worked out in §7.8), and a
   hand-made upload cannot be ear-splitting. No second BS.1770, no parity test between two
   implementations, no reference values to keep.
3. **Kept** in the KV store (§7.8), not on disk: a sound is at most 40 KB, KV writes are atomic, and it
   works whatever Mattermost's file storage is (Clips need local disk; sounds do not).
4. **Played** (`server/sounds_play.go`) by writing each stored packet onto gumble's connection with the
   exported `Conn.WriteAudio(4, 1, seq, final, packet, nil, nil, nil)` (U1), one every 20 ms on a
   ticker, the sequence counting 10 ms units (+2 per packet, U8), the last packet marked final, to voice
   target 1 (§7.4). Real-time pacing keeps it under Murmur's per-sender bandwidth meter (U9).

**No codec is registered with gumble.** Murmur accepts tunnelled Opus from a client that did not
advertise it, and leaves a client with no codecs out of its codec vote (U10;
`[MUM src/murmur/Server.cpp:1795-1809, 2391-2408]`, saved copy); a
registered stub would only change what the bot advertises. Fewer moving parts.

**Rejected, and why:**

- gumble's Opus codec, `gumbleffmpeg`, any libopus binding: cgo or an ffmpeg binary (U3).
- A pure-Go Opus **encoder** on the server (`tphakala/go-opus`, `pion/opus` main, `thesyncim/gopus`,
  `kazzmir/opus-go`): all build without cgo, but each is young, and an encoder is far harder to trust
  than a decoder with a conformance harness. Kept as Plan B (§7.18) if WebCodecs causes trouble.
- `MediaRecorder` and a WebM demuxer: real-time encoding of an upload, containers differing by
  browser, no control of the frame size, another dependency.
- Mixing two sounds at once: it would need decode, mix and re-encode on the server.

**New dependency:** `github.com/pion/opus v0.1.0` (MIT, pure Go, decoder only). `go.mod` and the
licence notes gain it; `govulncheck` runs over it at integration. Every call into it goes through one
function, `decodeChecked`, with `defer recover()`: a panic becomes 400 `bad_sound` and a Warn log line
naming the user id, never a dead plugin (three panics in an hour would deactivate VillaNET for
everybody, M17). Before adoption (B0) its decoder is fuzzed with raw packets for some minutes; the fuzz
target stays in the test suite (`FuzzDecodeChecked`).

### 7.3 Who is "in Mumble"

The panel and the server use **the headphones' rule** (V7): a Mumble name belongs to a Mattermost
account through **Names that differ** (`VoiceNameMap`), else, with **Match names to usernames** on, the
same username. `voiceUserID`'s rule is refactored into one function, `voiceNameMatches(name, username,
overrides, cfg)`, used by both the roster and the soundboard so they cannot disagree. Hidden names and
the bot's own never match.

**The rule gets stricter, for the headphones too.** 3.1.0 lowers a Mumble name with Go's
`strings.ToLower` before `GetUserByUsername`. Go maps `İ` (U+0130) to `i` and `K` (Kelvin) to `k`;
Murmur's own clash test uses Qt, which does not. So a stranger called `vİctor` can sit in Mumble beside
the real `victor`, and 3.1.0 matches both to Victor (U16). In 3.2.0:

- **By username:** only a Mumble name that is already plain `[A-Za-z0-9._-]{1,64}` can match, lowered
  with ASCII-only lowering. Anything else matches nobody. (Mattermost usernames are only those
  characters, M5, so no honest match is lost.)
- **By Names that differ:** the admin's Mumble name is compared with ASCII-only case folding; every
  other character must be identical. Never `strings.ToLower` or `strings.EqualFold`.
- **Exactly one session.** Murmur never keeps two sessions whose names are equal under its own
  lowering: a second one from the same IP or certificate replaces the first, and one from anywhere
  else is refused (U11). So with plain names, two matched sessions can only come from **Names that
  differ** mapping two Mumble names to one account. The soundboard treats that as ambiguous and
  refuses (`two_sessions`): one person, one Mumble client.
- The headphones gain the same rule, so a lookalike no longer shows headphones by somebody's name. That
  is one of two deliberate changes to 3.1.0's roster (A1).

**What a name proves, and what it does not.**

- What a match unlocks is the **pressing person's own** ability to play into the channel where the
  session with their name sits. The press is made in Mattermost, by an account that must be **linked**,
  and every play is logged with that account's id (§7.15). Nobody can act as somebody else in
  Mattermost through it, and listeners can always mute VillaNET in their own Mumble client.
- An unregistered Mumble name is first-come (U11). A stranger who takes "victor" while Victor is not in
  Mumble makes Victor's panel offer the soundboard, and lets **Victor** play into the stranger's
  channel. While Victor is in Mumble under that name, the stranger cannot connect with it.
- **Registration is weaker than it sounds.** On a default Murmur anybody may register a free name
  (U15), so **Only registered Mumble users** (`SoundsRegisteredOnly`, which needs `IsRegistered()`)
  helps only once your people have registered their own names, or an admin has taken SelfRegister
  away. Off by default; Q2 puts the choice to Victor, with its help text saying exactly this (§10.1).
- **If Victor wants a real binding (Q2 option c, not built unless chosen): pair once.** The soundboard
  sheet shows a one-time code (6 digits, 10 minutes); the person sends it to VillaNET's Mumble user as
  a text message; gumble's `TextMessageEvent` gives the sender's session, and the server stores
  `voicecert_<userId>` = that session's certificate hash (Murmur sends every user's hash to every
  client, U17). From then on the person's sounds need a matched session with that hash; **Forget my
  Mumble client** in the sheet deletes it. A certificate is held by the client's private key, so a
  stranger cannot present it.

### 7.4 Where a sound plays, and who hears it

**Into the presser's own channel, as a shout** (U6): voice target 1 is
`AddChannel(presserChannel, false, false, "")`, sent with `client.Send` when it differs from the target
last sent on this connection, and forgotten when the connection goes.

- Heard by everybody in that channel who is not deafened, and by anybody listening to it (Mumble 1.4+
  channel listeners). **The presser hears it too**: the shout leaves out only the sender, which is
  VillaNET.
- Not heard in any other channel.
- **VillaNET's Mumble account does not move.** It stays where Mumble parked it (usually the root), so
  nobody sees it join, and it does not start receiving that room's audio.
- A shout passes Mumble's "whispers from friends only" filter, which applies to whispers only.
- Everybody can mute or turn down "VillaNET" in their own Mumble client; the README says so.

Q5 offers the alternatives: always one channel an admin names, or the account moving into the channel.

### 7.5 The checks at a press

`POST /api/v1/sounds/play?id=<16 hex>`, linked. Cheap checks in memory first, then Mumble's live state,
then **one atomic admission**, and only then the costly work. Each refusal is a JSON error with a
`code` (words in §7.14) and, where it is about time, `retryAfterMs`.

1. **In memory:** the soundboard is on (`off`); the id is well formed (`bad_request`);
   `soundPressLimiter` allows it (30 a minute per person, `rate_limited`); the person is not blocked
   (`blocked`); the id is on the board as this node holds it (`gone`).
2. **A look at the gate**, changing nothing: the presser's own cooldown (`cooldown`) and the busy gate
   (`busy`), each with `retryAfterMs`. This only saves work; step 5 decides.
3. Mumble is connected on this node (`bot_offline`).
4. **One `client.Do`, from gumble's live state, never the published roster** (which lags up to 2 s,
   V8), as the function `voiceCheck(userID)` that the player calls again (§7.10):
   - the presser's sessions by §7.3's rule: none, `not_in_voice`; more than one, `two_sessions`; the
     one session muted or self-muted, `muted`; deafened or self-deafened, `deafened`; suppressed,
     `suppressed`; unregistered while `SoundsRegisteredOnly` is on, `not_registered`. Otherwise its
     channel is the target.
   - VillaNET's own session: muted, self-muted, deafened or suppressed, or logged in as SuperUser,
     `bot_cannot`. SuperUser is told **by name**, `client.Self.Name` equal to "SuperUser" under
     ASCII-only case folding: gumble's `UserID` is 0 for SuperUser and for an unregistered account
     alike, so a `UserID == 0` test would refuse every press from an unregistered VillaNET account
     (U17). Only the SuperUser password can log that name in.
   - Whisper in the target channel, when `Permission()` already knows it: without
     `PermissionWhisper`, `bot_cannot`.
5. **Admission: `soundGate.admit(userID, now)`**, one mutex, nothing else held. Under it, in order:
   (a) refuse `cooldown` when this user has a sound admitted or playing, or `cooldownUntil > now`;
   (b) refuse `busy` when a sound is admitted or playing anywhere, or `busyUntil > now`; (c) take the
   server-wide token from `soundGlobalLimiter`, else `too_many`; (d) mark the gate in flight for this
   user and set their `cooldownUntil` **provisionally** to now + `maxSoundMs` + 20 ms + the cooldown.
   All of it before the lock is released, so two presses sent at the same moment, from one person or
   five, give exactly one admission; the rest are told `busy` or `cooldown`.
6. **After admission** (any failure from here **undoes** it: the gate is freed, the presser's previous
   `cooldownUntil` comes back, and the server-wide token is refunded):
   - the blob is read (the 32-entry cache, else KV) and its checksum verified (`gone`, or `store` for
     a KV error);
   - Whisper not yet known: `RequestPermission()` and wait up to 1 s outside every lock; known and
     without `PermissionWhisper`, `bot_cannot`; still unknown after 1 s, play (Murmur would make it
     silent, and the admin card says so on its next check).
7. **Hand-off without a queue:** `select { case player.jobs <- job: default: undo; busy }`. The job
   channel holds nothing waiting; nothing ever stands in line.
8. **The player** (§7.10) runs `voiceCheck` again in the `client.Do` that sends packet 0, takes the
   target channel from **that** read, and fails the job with its code, sending nothing, if anything
   changed. The handler waits for the player's word and answers `{"startedAt", "endsAt",
   "cooldownUntil", "channel"}` once packet 0 is written, or the code.

**Refunds of the press token** (`soundPressLimiter`), only for refusals the presser could not see coming
and did not cause: `store`, `bot_offline`, `bot_cannot`, `gone`. Every other refusal (`cooldown`,
`busy`, `too_many`, `muted`, `deafened`, `suppressed`, `not_registered`, `not_in_voice`,
`two_sessions`) keeps it: the panel greys those out already, so an honest person rarely spends a token
on them, and a script pressing while muted or cooling down is held to 30 a minute. The **server-wide**
token is refunded whenever packet 0 never went out.

### 7.6 Cooldowns and limits

| Limit | Default | Where |
|---|---|---|
| Per person, after **their** sound ends | `SoundCooldownSeconds`, 10 (3 to 120) | `soundGate`, in memory, per node: `cooldownUntil` per user id, set provisionally at admission and corrected to the real end + the cooldown when the sound ends |
| Sounds at once, server-wide | **1**, then 250 ms of quiet; a press meanwhile is refused (`busy`, with `retryAfterMs`), never queued | `soundGate`: one in-flight mark and `busyUntil` |
| Sounds a minute, server-wide | 8 (`soundGlobalLimiter`, one bucket), taken inside the admission | `rateLimiter` keyed `""` |
| Presses a minute, per person | 30, refunded only for `store`, `bot_offline`, `bot_cannot`, `gone` (§7.5), so it bounds refused presses too | `soundPressLimiter` |
| Uploads, per person | 20 an hour | `soundUploadLimiter` |
| Renames, emoji changes and deletes, per person | 30 a minute | `soundEditLimiter` |
| Longest sound | 6 s: **301 packets**, because the encoder's delay adds one (W2) | Code constant `maxSoundMs` = 6000; the packet cap is `maxSoundMs/20 + 1`; Q6 |

`rateLimiter` cannot say how long until the next token (V20), so the cooldown and the busy gate live in
`soundGate`, which returns the time left; the per-minute caps answer `retryAfterMs` from a new
`rateLimiter.wait(key, now)` helper that reads the bucket without taking a token. `soundGate` is one
struct behind one mutex (`admit`, `undo`, `started`, `ended`); no other code reads or writes its
fields.

### 7.7 Whose sounds

**One shared board** for the server (Q4). Everybody it is for sees and plays every sound.

- **Who sees it:** linked people **in Mumble now**. `GET /sounds` answers every linked caller their
  voice state, and the list only to somebody matched to a Mumble session at that moment, in any state
  (muted people still see the board, greyed). This is Victor's "unlock" held by the server, not only by
  the panel.
- **Add:** linked, the soundboard on, not blocked, and **in Mumble now** (a matched session in any
  state, read live as §7.5 step 4 reads it; `not_in_voice` otherwise). At most **16 sounds a person**
  and **120 in all**.
- **Rename and change the emoji:** the person who added it, in Mumble now.
- **Delete:** the person who added it (open: a takeback, even after they unlink or leave Mumble), and
  system admins in the System Console. **Delete my sounds** (`POST /sounds/remove-mine`, open) deletes
  all of somebody's own at once, offered under the sheet's grid (§7.13) and in their own profile
  popover (§4.6), so somebody who has unlinked or left Mumble can still reach it.
- **Listen here** plays a sound in the presser's own browser: their own sounds only
  (`GET /sounds/audio` is owner-only; admins have their own route).
- **Order on the board:** oldest first, so tiles never move under people's fingers; a new sound is
  added at the end.
- **When somebody's account is deactivated or they unlink**, their sounds stay on the board; admins
  delete what should go.

### 7.8 Data

**`sounds`** (one KV document, §2.1):

```json
{"v":1,
 "entries":[{"id":"9f2c…16hex","owner":"<userId>","name":"Airhorn",
   "emoji":{"kind":"system","name":"loudspeaker","unified":"1f4e2"},
   "ms":2400,"bytes":24600,"level":-21.3,"at":1760300000000}],
 "blocked":{"<userId>":{"by":"<adminId>","at":1760300000000}}}
```

- `emoji` is `{"kind":"system","name","unified"}` or `{"kind":"custom","name","id"}`, always filled in by
  the server from its own lookup, never from the client's word: a system emoji by
  `model.GetSystemEmojiId(name)` (M9); a custom one by `p.API.GetEmojiByName(name)`, and only while
  Mattermost's custom emoji are switched on (`ServiceSettings.EnableCustomEmoji`).
- `name`: 1 to 16 characters after trimming, one line, control characters refused, the author's own
  bearer token and stream key removed first (`cleanTyped`, as plan titles).
- Written by `casUpdate`; held in memory, refreshed after a write and at most every 30 s.

**`sound_<id>`**, one per sound, the packets:

```
"VNS2"  i64 addedAtMs  u16 count  u8 frameMs(=20)  [32]byte sha256(packets section)
        then count × (u16 length, bytes)
```

`ms` is `count × 20` (so a full 6 s trim, 301 packets, reads 6020 and is shown as "6.0 s"); `level` is
the server's whole-sound level from the ceiling check below, for the admin card.

**The upload**, `POST /api/v1/sounds`, body at most 80 KB (`http.MaxBytesReader`), strict JSON:
`{"name","emoji":{"kind","name"},"packets":"<base64 of: u16 count, then count × (u16 length, bytes)>"}`.
The server refuses, with `bad_sound` unless said otherwise:

| Check | Limit | Why |
|---|---|---|
| Decoded packets section | at most 40 000 bytes | 301 × 130 = 39 130 |
| Count | 13 to **301** (`maxSoundMs/20 + 1`) | 0.25 s gives 13 and a full 6.00 s gives 301, because the encoder's delay adds one packet (W2) |
| Each packet | 1 to 128 bytes | (128 + 32) × 50 × 8 = 64 kbit/s, under the 72 kbit/s an old Murmur configuration allows (U9); 40 kbit/s CBR gives 100 |
| Each packet's TOC byte | `p[0]&3 == 0` (one frame), `p[0]&4 == 0` (mono), and a 20 ms configuration (`p[0]>>3` one of 1, 5, 9, 13, 15, 19, 23, 27, 31) | Exactly what WebCodecs makes (W2: `0x78`, `0xF8`). `PacketDuration2 == 960` alone would also pass 2×10 ms, 4×5 ms and 8×2.5 ms packings and stereo (U14), which no honest panel sends and every listener's decoder would have to parse |
| Decode | every packet decodes with pion into 960 samples, inside `decodeChecked` (a panic is `bad_sound`, §7.2) | Real Opus, nothing else |
| Whole-sound level | K-weighted, **ungated**, not above **−14** (`too_loud`) | The panel makes −20 LUFS **gated**; an ungated level is never above the gated one, so an honest sound is at or under −20: 6 dB of margin |
| Loudest 400 ms window | K-weighted, every window stepping by 100 ms (a shorter sound is one window padded with silence), not above **−5** (`too_loud`) | Gating lets an honest 6 s sound hold one 400 ms burst up to about 11.3 dB above its integrated −20, so about −8.7; −5 leaves 3.7 dB. A short blast cannot hide in a quiet sound |
| Silence | no 400 ms window above −50 (`silent`) | An honest sound has a block within 10 dB of −20 |
| Name, emoji | as above (`bad_name`, `bad_emoji`) | |
| Room | 16 a person (`yours_full`), 120 in all (`full`) | |

**Why K-weighted and not plain RMS.** K-weighting is BS.1770's two filters (a shelf and a high-pass,
fixed coefficients at 48 kHz), about 20 lines of Go. Plain RMS would read bass far louder than the
browser measured it: K-weighting takes 5.6 dB off 40 Hz, 8.3 dB off 30 Hz and 13.3 dB off 20 Hz, so an
honestly levelled bass-heavy sound could fail a plain-RMS ceiling. Using the same filters on both sides
keeps the margins above true without a second BS.1770 (no gating, no blocks overlap rule, no parity
test, no reference values).

**Orphans.** The blob is written first, then the document; if the document write fails, the blob is
deleted. At activation, while the soundboard is on, a sweep deletes `sound_` keys that have no entry,
**only when the `sounds` document was read and decoded in this activation** (never after a store error
or a quarantine, when no blob would have an entry), and **only for blobs added more than 10 minutes
ago** (the header's `addedAtMs`; a blob without a readable header counts as old), so an upload in
progress on another node is never swept. The count deleted is logged.

### 7.10 The player

One player per held Mumble connection (`holdVoiceConnection`), started when the connection is up and
stopped by its `defer` and by `stopVoice`, so a sound never outlives its connection or its epoch (V8).

- An **unbuffered** job channel, sent to only with a non-blocking `select` after admission (§7.5 step
  7): a job is taken only while the player is idle, and nothing ever waits in a queue.
- **Before the first packet, in one `client.Do`:** `voiceCheck(presser)` runs again **in full** (§7.5
  step 4: the presser's one session, its muted, deafened, suppressed and registered state, VillaNET's
  own state), and the target is the channel **that** read finds, not the one found at the press. Any
  refusal fails the job with its code, **with zero packets sent**, and undoes the admission. The voice
  target is re-sent there when it changed.
- **Sequence.** As Mumble's own client counts frames through silence (U8): `seq = lastSeq +
  round(sinceLastPacket / 10 ms)` when the last packet was less than 5 s ago, otherwise 0; then +2 per
  packet.
- A `time.Ticker` of 20 ms. **Every tick** first reads the presser's session again in `client.Do` (a
  read lock over gumble's maps, cheap at 50 a second; `WriteAudio` takes the connection's own write
  lock separately, U1). If they have muted, deafened, become suppressed, left, or moved to another
  channel, this packet goes out marked final and the sound stops there; otherwise it writes the packet
  with `client.Conn.WriteAudio(4, 1, seq, last, packet, nil, nil, nil)`. A write error stops the sound
  and is logged at Warn. Victor's rule is about not abusing the sounds; a sound that follows its
  presser out of the room, or plays on after they mute, is that abuse.
- When it ends (or stops): `soundGate.ended` frees the gate, sets `busyUntil` to now + 250 ms and the
  presser's `cooldownUntil` to the end + the cooldown (correcting the provisional value), and the
  `sound` event goes out (§2.3). A job that fails before packet 0 calls `soundGate.undo` instead, and
  the server-wide token is refunded.
- **The `sound` event** `{"busyUntil"}` goes, at the start and the end, to every Mattermost account
  matched in the current roster (`WebsocketBroadcast{UserId}`, a handful at most). It names no sound and
  no person: the panels of people in voice use it to grey the tiles while something plays.

  window when it is pressed, because 6 s of a 2-minute clip is about 10 px at 304 px.
- **Names run to two lines** in every tile style (wrapping at spaces, so a 16-character name shows
  whole); an A tile is 74 px tall rather than square.
- **The cooldown look**: the tile you pressed gets a sweep and the seconds left in its corner, the
  others dim, and a grey bar drains under the head. This replaces a grey ring draining on every tile,
  which the preview found too busy. Somebody else's sound keeps the red bar. The bar always keeps its
  place (hidden when idle), so the sheet's height never changes on a press.
- **Visible head lines** while the tiles wait: "Ready again in {n} seconds" (the screen readers' line,
  also shown) and "Another sound is playing." (the first sentence of the `busy` line; nothing can be
  pressed meanwhile). While your own sound plays, the head keeps "Plays in {channel}".
- **ADD and Delete all my sounds while the tiles are off**: **Delete all my sounds** shows whenever the
  reader has sounds, in every state (it is a takeback, §7.7). The ADD tile and the empty board's

  **Change emoji** the chooser. A refused delete says its refusal's words.

### 7.15 Security

- **Linked only**, by the gate and by `requireLinkedStream`, and **in Mumble now** for the board, adding
  and renaming (§7.7); takebacks (delete your own, delete all your own) open. Admin routes check
  `isSystemAdmin` first.
- **The mute rule is the server's**: §7.5 step 4 reads gumble's live state at the press, the player
  reads it again before packet 0 and before every packet after (§7.10); the grey tiles are a courtesy.
  Suppressed counts as muted (§7.5), and the roster's `muted` gains `Suppressed` too, so the headphones
  turn slate for somebody Mumble will not let speak, and the grey tiles match the server.
- **Names:** plain-letter names only, ASCII-only lowering, exactly one matched session (§7.3); what a
  name does and does not prove is in §7.3 and the help text.
- **Concurrency:** admission is one mutex (§7.5 step 5); presses sent together give one sound, and the
  cooldown and the 250 ms gap hold under any number of tabs or scripts.
- **IDOR:** edit and remove check the owner; play is for any sound on the shared board, by somebody in
  Mumble; audio is the owner's alone (admins have their own route).
- **Upload validation:** §7.8, every byte checked, the TOC held to one mono 20 ms frame, every packet
  decoded with a panic caught, sizes bounded at each step, strict JSON, the emoji resolved on the
  server.
- **Storage caps:** 120 sounds × 40 KB, under 5 MB of KV; 16 a person; a blocked list of 50.
- **Abuse:** §7.6's limits; admins block and delete; listeners mute VillaNET locally.
- **Logging:** Info "Played a sound" with `user_id`, `sound_id`, `ms`; Info on add and delete with the
  same ids; Warn on a caught decoder panic with `user_id`. Never a Mumble password, certificate hash,
  stream key or token. Sound names are not logged.
- **CSRF and images:** the non-GET routes need Mattermost's CSRF token. The two audio GETs answer only
  `madeByScript`, before their meter, so a Markdown image pointing at one spends nothing and reads
  nothing; they carry 3.1.0's file headers and `private, no-cache`, so a sound deleted, a person
  blocked or a reader unlinked is never served from a browser cache without the checks running again.
- **No browser contacts anybody new:** emoji images and the sound itself come from Mattermost's origin;
  encoding happens in the browser.

### 7.16 Privacy

- The board (names, emoji, who added each) is seen by linked people in voice, and the server holds it
  to that (§7.7, §7.9). A sound's audio is fetched only by its owner and by admins. Who **played** what
  is told to nobody but the log: the `sound` event names neither sound nor person, and Mumble listeners
  hear "VillaNET".
- A person's Mumble channel name goes only to that person (`GET /sounds`), and to admins in a bot
  alert.
- Sounds stay in the KV store until deleted; they are not in the settings backup.

### 7.18 Risks

- **Nothing here has met a real Mumble server.** Victor's server version, ACLs and bandwidth setting
  decide whether sounds are heard (Appendix A; §13.2 V1-V9 come first on the real server).
- gumble is unmaintained since 2022; the one function used (`WriteAudio`) is small and exported. Its
  old self-deadlock (U12) is unchanged by this work.
- The legacy voice format is Mumble's path for clients older than 1.5; 1.6.870 keeps it (U10). A future
  Mumble that drops it would silence sounds, not break the roster.
- A Murmur configured with an `opusthreshold` that elects CELT would drop Opus (rare; the admin card's
  check cannot see it; the README mentions it).
- WebCodecs is needed only to **add** a sound: Chromium and the desktop app 119+ (constant bitrate),
  Firefox 130+, Safari 26+, not Firefox for Android (W1). Playing works from any browser.
- `pion/opus` is young; a panic is caught (§7.2) and fuzzing runs before adoption, but a decoder bug
  that loops rather than panics would hold one request. Uploads are 20 an hour per person, and the
  review's runs saw a slowest packet of 2.6 ms.
- **Plan B** if WebCodecs or pion causes trouble in the lab: upload 16-bit PCM (about 576 KB for 6 s,
  so the body cap rises to 640 KB) and encode on the server with `github.com/tphakala/go-opus` v1.1.0
  (BSD-3, CELT, pure Go). One place for every rule, at the price of trusting a young encoder.
- A Mattermost cluster: only one node can hold the Mumble name (research; `server/plugin.go:645`), so a
  press reaching another node answers `bot_offline`. Single server is the target, as for airtime.

## 8. Feature 7: @names in stream titles

### 8.1 What it is

`@dave` in a stream title becomes pressable, the way `#arma3` is: where a hashtag in a title opens
Mattermost's search for it, an @name opens **Mattermost's own profile popover** for that person, which
already holds VillaNET's live row (Live now with Watch, awards, plans) and Mattermost's Message and Call.
Nothing is sent to anybody.

### 8.2 Parsing (`webapp/src/titleParts.ts`, pure, no imports)

The finders for links, hashtags and now mentions, and `linkParts`, move out of `linkify.tsx` into
`titleParts.ts`, which imports nothing (`linkParts` takes the hashtag minimum as a parameter, which
`linkify.tsx` passes from `hashtagMinimum()`), so a check script can load it as `check-twitch.mjs`
loads `twitchLogic.ts`. `linkify.tsx` keeps the drawing.


- **Mattermost's rule** (M5): `/(?:\B|\b_+)@([a-z0-9.\-_]+(?::[a-z0-9.\-_]+)?)/gi`. So `user@host` and
  `mailto:a@b.c` are not mentions (the `@` follows a word character), exactly as in a post.
- A match with a `:remote` part stays plain text (shared-channel names mean nothing here).
- Trailing `.`, `-` and `_` are given back to the sentence ("@dave." is `@dave`), as `AtMention` does.
- `all`, `channel` and `here`, in any case, stay plain text and are never a person or a broadcast.
  Mattermost's other reserved names (`matterbot`, `system`) are left to Mattermost, which has nobody by
  those names.
- What is left must match `^[a-z0-9._-]{1,64}$` after lower-casing, or it stays plain text.
- **An address wins**: a mention inside a link span is dropped, as hashtags are (`twitch.tv/@x`).
  Hashtags and mentions cannot overlap (`#` and `@` both start their own spans).
- `LinkPart` gains `mention?: string` (the lower-cased name); `linkParts` merges the three kinds of span
  in order. `hasLinks` counts mentions too, so a title with one stops being a toggle button, as with a
  link.
- **Twitch cards** (`stream.source === 'twitch'`): no mentions are made at all. Twitch titles use @ for
  Twitch handles, and a Mattermost account with the same name would be the wrong person.

### 8.3 Drawing, and where

`renderPart` draws a mention as:

```tsx
<span className='vntv-mention' onClick={stop} onKeyDown={keepKey}>
    {window.PostUtils.messageHtmlToComponent(
        `<span data-mention="${name}">@${typed}</span>`,
        {mentions: true, mentionHighlight: false, disableGroupHighlight: true, fetchMissingUsers: true,
         emoji: false, images: false, latex: false, inlinelatex: false, markdown: false})}
</span>
```

- `name` and `typed` (the text as written, case kept, without its trailing punctuation) contain only
  `[A-Za-z0-9._-]`, which is why they may be put into HTML: nothing in them needs escaping, and the
  parser never lets anything else through. **A title is never given to `formatText` or to
  `messageHtmlToComponent` whole**: titles come from Broadcast Box, Twitch and admin notes, not only
  the panel.
- The wrapper stops a click, and Enter or Space, from reaching the card or ticker it sits in, because a
  portalled popover's events still bubble through React's tree (M4). It lets every other key through,
  as links do.
- `window.PostUtils` missing (the lab, a future Mattermost): the mention is drawn as plain text in the
  mention style, not pressable.
- **The ticker's second copy** (`aria-hidden`, inert) never draws an `AtMention`, so it adds no tab
  stop and no popover. It draws each mention as plain styled text **equal to what the first copy
  shows**: after each measure, `Marquee` reads the live copy's mentions' `textContent` in order (it is
  text, never HTML) into component state, and the inert copy draws mention *i* with that text, or
  "@" and the typed name until it is known. Otherwise the first copy would read "@Dave Ryder" and the
  second "@dave", the two copies would differ in width, and the loop would jump at the seam.
- Styled inside the panel: `.vntv .mention-link` takes the panel's link colour and underline on hover,
  matching `.vntv-hashtag`; Mattermost's highlight is off.

**Where:** exactly where hashtags are pressable. The tile ticker (`Hud` `Marquee`, both copies as
above) and the Live now card's controls line (`vntv-live-links`), where a mention in the middle of a
title stays in the words line as text and gets its own control on the links line, as hashtags do.
**Not** the footer's own title (it is a button), tooltips, a clip's stream note, plan titles, or the
popover. (Plan titles are not linkified today; that is unchanged.)

### 8.4 What pressing does, and caches

Mattermost's `AtMention` (M4): it finds the person in Mattermost's store, asks Mattermost's own batched
loader for anybody missing (`POST /api/v4/users/usernames`, same origin), and on a press opens the
profile popover, portalled above the panel (z-index 1200 against the panel's 1065 at most) and closed
by a click outside or Escape, with focus returned to the mention.

- **The name shown is Mattermost's.** `AtMention` writes `@` and the person's name as the server's
  **Teammate Name Display** setting says, so with names shown in full "@dave" reads "@Dave Ryder" once
  it is found, which changes the words' width with the same title in the same box. Today's `Marquee`
  would not notice: it measures when the text changes or its outer box resizes, and the box is clipped
  and never resizes (V34). So its `ResizeObserver` also observes the words span (`wordsRef.current`),
  and every measure refreshes the inert copy's mention texts (§8.3). Q12 asks Victor whether the
  display name is acceptable.
- **Unknown names** stay as typed, plain, not pressable.
- **No VillaNET cache.** Everything looked up lands in Mattermost's own store, which Mattermost manages
  across sign-in and sign-out. So the 3.1.0 sign-out rule has nothing new to forget for mentions, and
  `check-away.mjs` holds `titleParts.ts` and `linkify.tsx` to holding no module-level map or set (§2.6).

### 8.5 Notifications

**Nobody is notified.** A title is not a post, and Mattermost raises mentions only from a post's message,
attachments and block text (M6). VillaNET puts no title into any post: the clip and plan shares' message
text is fixed, and their props are never parsed. `TestNoShareMessageCarriesATitle` holds both. Q12
offers a quiet in-panel nudge instead, if Victor wants one.

### 8.6 Words

None of VillaNET's own: the mention reads as written or as Mattermost names the person. The README
explains it (§10.2).

### 8.7 Tests and lab

`build/check-mentions.mjs` (new) over `titleParts.ts` (the mention finder and `linkParts`): Mattermost's
regex cases (start of text, after punctuation, after `_`, `user@host`, `mailto:`); trailing `.`, `-`,
`_`; `@all`, `@ALL`, `@channel.`, `@here!`; `@name:server`; 65 characters; an address winning
(`https://twitch.tv/@x`, `www.example.com/@x`); a hashtag and a mention side by side; a Twitch card
making none; the HTML handed to `messageHtmlToComponent` matching `^<span data-mention="[a-z0-9._-]+">@[A-Za-z0-9._-]+</span>$`
for every case.

Lab: a stand-in `window.PostUtils.messageHtmlToComponent` that draws a button for the lab's people
(u-victor, u-dave, u-bob, u-erin) opening a mock popover with `PopoverLive` in it, and plain text for
anybody else; titles "Arma night with @dave and @bob #arma3", "@all welcome", "mail me@example.com",
"https://twitch.tv/@dave"; the ticker and the Live now card at 304 and 400 px; a Twitch card with an
@handle; and a stand-in whose "@dave" first draws as typed and **resolves to "@Dave Ryder" 500 ms
after the first measure**, so the ticker is seen to re-measure and both copies to read the same.

### 8.8 Risks

- `window.PostUtils` is public and untyped; it is feature-detected and has a plain fallback. Only 11.11
  is supported, which lowers the risk.
- The popover from inside the RHS, its popout windows and the ticker needs the real-server check
  (§13.2 V12): focus return, Escape, stacking against the panel's sheets.

## 9. Feature 8: a thumbs up on shared clip posts

### 9.1 What it is

A clip shared into a channel gets its upvote right on the post card: the count, and for a linked reader
a thumbs-up button that votes exactly as the panel's does. **The vote rules do not change**: only linked
people vote (server-enforced), a vote counts only while the voter is linked, the clipper's own never
counts, nobody votes on their own clip.

Mattermost's native 👍 reaction is a different thing and stays one: reactions cannot be refused by a
plugin (M2), anybody in the channel can add one, and they would never match "only while linked".

### 9.2 Server: the cards route says more

`clipCardView` (V15) gains three fields:

```go
Upvotes int  `json:"upvotes"`           // displayedUpvotes: voters who count now; the same for everybody
Voted   bool `json:"voted,omitempty"`   // this reader has voted (still shown for a let-in reader's old vote)
CanVote bool `json:"canVote,omitempty"` // linked, not a bot, not their own clip
```

`handleClipCards` now uses the key it is given (V15): `clipViewerOf(userID, key, now)` once per request,
and `CanVote` is false for a let-in reader (`WatchOnly`), a bot, and the clipper. The answer becomes
per reader, so it gets `Cache-Control: no-store` (it is already fetched with credentials only). Votes go
through the existing `POST /api/v1/clips/vote` and its `voteLimiter`; nothing else changes on the
server. Props stay as they are: **no count ever goes into a post** (M11).

### 9.3 Webapp

- The shared-card cache entry (`SharedCard.card`) carries the three fields.
- `ClipPostCard` gains the thumb, after Watch in its actions row (preview P6 shows it there, and in the
  meta line):
  - linked and `canVote`: `<button className='vntv-postclip-thumb' aria-pressed={voted}>` with
    VillaNET's thumb (the panel's `UpvotePill` shape, its svg `pointer-events: none`) and the count;
  - linked on their own clip, or let in: the same pill as a static `role='img'` count;
  - locked, gone, fallback, or a card still waiting: nothing.
- **Voting from the card**: `voteOnCard(id, up)` in `clips.ts` patches the shared card at once (and the
  Clips dialog's copy in `byId` when the dialog holds that clip), posts the vote, applies the answer
  `{upvotes, voted}` to both, and on failure puts both back and shows "Couldn't count that. Try again."
  under the card for 8 s. A vote in the dialog patches a shared card the same way. One function owns
  the optimistic patch so the two copies cannot disagree.
- The button is a real `<button>` (a click elsewhere inside a permalink preview follows the permalink,
  `ClipPostCard.tsx:47-52`).

### 9.4 Fresh for everybody, without the storm

The reader's own presses apply at once. For everybody else's:

- **When `snapshot.clips.version` changes** (every vote changes it, V15), the cards **currently mounted**
  (`cardsShown`; the centre channel's post list is a `DynamicVirtualizedList` that mounts only the posts
  near the screen, `[MM components/post_view/post_list_virtualized/post_list_virtualized.tsx:700-710]`) are asked again, in
  one batched request of up to 25 ids, after a random wait of up to 3 s, **at most once every 30 s per
  page**, and only while the page is visible (`document.visibilityState`).
- The 3.1.0 rules stay for everything else: on mount after 10 minutes, on Watch, when a clip goes.
- That is review fix #3's concern answered: no card off screen ever asks, a busy evening of votes costs
  each open page at most two requests a minute, and the requests are spread out.

### 9.5 What each reader sees

| Reader | On the web card | On the mobile app, push, email, Threads |
|---|---|---|
| Linked | The thumb button with the count; pressed if they voted | The post's fixed text and link (M10); no count |

| Locked | No count (the card is drawn from props, which never carry one, and makes no request) | The same |

### 9.6 Words

  up. Click to take it back."
- Static: name "{n} thumbs up"; tooltip on your own clip "Thumbs up on your clip".

  `rate_limited`, `gone`).

## Appendix B: the WebCodecs probe page

The page B0 copies into the project as `build/wcprobe.html` (§12.2) and opens in headless Chrome and in
Firefox. It reports whether constant-bitrate Opus is supported, the packet counts for 0.25, 1, 5.99 and
6.00 s (expected 13, 51, 300, 301, all 100 bytes, W2), and the six fixture signals as base64 packets in
`window.__probe`, which a driver script saves as `server/testdata/sound-<engine>-40k.json`. The noise is
seeded, so a fixture can be made again.

```html
<!doctype html>
<meta charset="utf-8">
<title>VillaNET WebCodecs probe</title>
<pre id="out">running</pre>
<script>
// The contract's encoder settings (§7.2 step 1.4).
const CBR = {codec: 'opus', sampleRate: 48000, numberOfChannels: 1, bitrate: 40000,
    bitrateMode: 'constant', opus: {frameDuration: 20000, complexity: 10}};

function seeded(seed) {
    let s = seed;
    return () => { s = (s * 1103515245 + 12345) & 0x7fffffff; return s / 0x7fffffff; };
}

// tone: 440 Hz. noise: seeded noise under a 3 Hz envelope, speech-like in rhythm.
function signal(kind, seconds, amplitude) {
    const n = Math.round(seconds * 48000);
    const pcm = new Float32Array(n);
    const rnd = seeded(1);
    for (let i = 0; i < n; i++) {
        const t = i / 48000;
        pcm[i] = kind === 'tone' ?
            amplitude * Math.sin(2 * Math.PI * 440 * t) :
            amplitude * (rnd() * 2 - 1) * Math.abs(Math.sin(2 * Math.PI * 3 * t));
    }
    return pcm;
}

async function encode(pcm) {
    const packets = [];
    const encoder = new AudioEncoder({
        output: (chunk) => { const b = new Uint8Array(chunk.byteLength); chunk.copyTo(b); packets.push(b); },
        error: (e) => { packets.error = String(e); },
    });
    encoder.configure(CBR);
    encoder.encode(new AudioData({format: 'f32-planar', sampleRate: 48000, numberOfFrames: pcm.length,
        numberOfChannels: 1, timestamp: 0, data: pcm}));
    await encoder.flush();
    encoder.close();
    return packets;
}

const base64 = (b) => btoa(String.fromCharCode(...b));

(async () => {
    const out = {ua: navigator.userAgent};
    const support = await AudioEncoder.isConfigSupported(CBR);
    out.supported = support.supported;
    out.bitrateMode = support.config && support.config.bitrateMode;

    out.counts = {};
    for (const seconds of [0.25, 1, 5.99, 6]) {
        const p = await encode(signal('tone', seconds, 0.15));
        const lengths = p.map((x) => x.length);
        out.counts[seconds] = {count: p.length, min: Math.min(...lengths), max: Math.max(...lengths)};
    }

    // Expected at the server (§7.8): the first four pass, "loud" is too_loud, "quiet" is silent.
    out.fixtures = {};
    for (const [name, kind, seconds, amplitude] of [
        ['tone1s', 'tone', 1, 0.15],      // -20.2 LUFS before encoding
        ['noise2s', 'noise', 2, 0.15],    // -21.1
        ['blip', 'tone', 0.25, 0.15],
        ['full6s', 'noise', 6, 0.15],     // must be 301 packets
        ['loud', 'tone', 1, 0.9],         // -4.6
        ['quiet', 'tone', 1, 0.0005],     // -69.7
    ]) {
        out.fixtures[name] = (await encode(signal(kind, seconds, amplitude))).map(base64);
    }

    window.__probe = out;
    document.getElementById('out').textContent = JSON.stringify({counts: out.counts,
        supported: out.supported, bitrateMode: out.bitrateMode}, null, 1);
})().catch((e) => {
    window.__probe = {error: String(e)};
    document.getElementById('out').textContent = 'ERR ' + e;
});
</script>
```
